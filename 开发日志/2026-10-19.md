## 四、TC-F6 补上真实计时，顺带把 K-07 问住了

"我能自己实测"那五条里先做了 F6（PowerShell 计时到主窗口句柄出现）：
Release 构建（`19454dd`）连测三次 **0.92 / 0.65 / 0.61 秒**。判据"第二次及以后 ≤2 秒"满足。

但第一次也这么快，跟 K-07 写的"首次启动 10~30 秒"对不上。于是删掉单文件解包缓存
（`%TEMP%\.net\RouteQuery`）再测：**冷启动 0.70 秒，热启动 0.62 秒**——差 0.08 秒，不是量级差。
道理也说得通：.NET 8 单文件配 `IncludeNativeLibrariesForSelfExtract` 只解原生库，
程序集从包体内按需读取，根本没有"先把整个运行时解压出来"那一步。

**K-07 先不删。** 两个理由：① 我这台机器上它当初可能是真的（早期构建、杀软首扫、机械盘都可能），
一次反证不足以推翻一条来自实测的记录；② 更要紧的是 **K-07 已经写进 `使用说明.txt`**——
"第一次打开会慢一些（约 10~30 秒）"。如果它现在不成立，那句话就是在误导亲友，
而误导的方向还不唯一（有人会因为等不到而以为程序坏了，去双击第二遍）。
**下一步**：在另一台机器或亲友首装时记一次真实首启耗时；确认没有 10~30 秒就改掉使用说明里那句，
而不是留着一条没人验证过的"已知代价"。

F6 的"无白屏"那半句仍欠——计时测的是"窗口句柄出现"，不等于"绘制完成且中间没有空白帧"。
所以这条从"完全未验证"移到"实测通过 + 欠肉眼一半"，**"需要有人参与"的总数不变，仍是 11**。

### 查出来的 bug：中止时界面会说" + Q + "未查候选 0 个" + QQ + "

`ExtensionBatch.CandidatesNotQueried` 原来算的是 `candidates.Count - taken.Count`，
也就是" + Q + "**超出本轮预算**的候选数" + QQ + "。整批被风控中止时这个数往往是 0，而真正没查的那几个
（预算内、循环里 break 掉的）一个都没被计进去——**界面与日志于是写出" + Q + "未查候选 0 个" + QQ + "，
把用户最该知道的那件事正好说反**。改成 `candidates.Count - outcomes.Count`：
正常跑完时两式等价（`outcomes.Count == taken.Count`），所以既有测试一条没改判；
新测试里那句 `Assert.Equal(2, batch.CandidatesNotQueried)` 才是它真正的行为。

这个 bug 不是谁报的，是" + Q + "写测试顺手查出来的" + QQ + "——而它已经在 rc1 和 rc2 的包里躺着了。
