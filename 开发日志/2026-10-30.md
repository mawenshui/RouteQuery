## 二、这一轮真正值得记的一件事：转换器口径漂移，只有逐字节比对才会露

随包的 `使用说明.txt` / `变更日志.txt` 由 md 生成，但**生成脚本从来没进过仓库**——每轮在 `D:\tmp` 现写一遍。
这次我先做了一件以前没做的事：**拿上一版的 `使用说明.md` 转出 txt，与 rc3 包里那份 txt 逐字节比对**。

第一次跑，406 行差异。全部看完，是三处口径不同：

1. 换行——包内是 CRLF，我写成了 LF；
2. 表格行——包内用**四个空格**拼两列，我用成了制表符；
3. `> ## 先读这一段…` 这种**引用里套标题**的记号，我只剥了 `>` 没再剥 `##`。

三处都不报错、都不影响"能打开"，肉眼在记事本里也看不出差别——**但随包文件的字节和上一轮记录的对不上了**。
改齐之后才一致（6375 字符逐字节相同），然后才生成 rc4 的两份 txt，禁词断言两份都过。

**结论一句话**：这类"没有脚本、每次现写"的工序，正确性只能靠一个自证的比对步骤兜住，
而那个步骤本身必须便宜到愿意每次做。**下一轮出包前先把转换器落成仓库里的脚本**——
这是连续第六轮手工出包，也是第六次靠现场写的脚本出包。

## 三、`git push` 推不上去：上一轮我给的原因是我编的，今天查出来是另一回事

昨天我写的是"远端走的是 GCM 里那份旧凭据，只有带 token 的内联 URL 能推"。**这句是错的**，
而且错在两个地方，今天一条命令一条命令查出来：

1. **github.com 的凭据助手根本不是 GCM。** `git config --list --show-origin` 显示用户级
   `.gitconfig` 里有 `credential.https://github.com.helper=`（空值，用来**清掉**系统级的 `manager`）
   紧跟一行 `…helper=!'C:\Users\MWS\Apps\gh\bin\gh.exe' auth git-credential`。
   也就是说走的是 **GitHub CLI 的凭据助手**，`cmdkey /list` 里也确实没有 github 条目。
2. **失效的不是钥匙串里的凭据，是一个旧的环境变量。** `gh auth status` 说
   "Failed to log in … using token (**GITHUB_TOKEN**) — The token in GITHUB_TOKEN is invalid"。
   比对之后定位到根因：本会话从 Qoder 进程**继承**下来的 `GITHUB_TOKEN` 与用户级环境变量里那份
   **长度都是 93、值却不同**——继承的那份是轮换之前的旧 token。
   `gh` 优先用环境变量，所以旧值一直把钥匙串里那份好凭据挡在后面。
   同时验证了用户级那份**确实是有效的**：`GET /user → 200`，`push --dry-run` 也报得出
   `785590a..a9a1033`。**同一天里"token 无效"和"token 有效"两个结论同时成立，因为它们说的是两份不同的 token。**

**修法**：把用户级那份有效 token 灌进 gh 自己的凭据存储（`gh auth login --with-token`，
落到 Windows 钥匙串），此后 `git push origin main` 走助手即可，不再需要内联 URL。
实测 `env -u GITHUB_TOKEN git push --dry-run origin main` 已经能算出正确的推送范围。

**还留着的一个坑，我没有擅自处理**：用户级环境变量 `GITHUB_TOKEN` 现在与钥匙串里是**两份重复的凭据**。
只要它存在，`gh` 就永远优先读它——**下次轮换 token 时如果只更新了钥匙串而忘了它，今天这种
"看着配好了其实一直在用旧值"会重演一次**。建议把它删掉，只留钥匙串一处。
删它等于撤销用户昨天明确让我做的事（"将其写到环境变量中"），所以这一步等用户点头。
另外：**这个 token 已经在聊天里贴过一次，轮换掉更稳妥**；本会话继承的那份旧值随 Qoder 重启才会消失。

## 四、这一天里我差点又判错的两次

- **zip 字节数比 rc3 大了 2 MB**（68,304,675 vs 66,227,101），而 exe 字节数一模一样。
  第一反应是"压缩出问题/混进了多余文件"。**先查成员构成再下结论**：包内正好三个文件，
  每个的解压内容与源文件逐字节相等，UTF-8 文件名标志位 `0x800` 也在。
  差的 2 MB 来自压缩级别（这次是 Python `zipfile` + deflate level 6，上一轮不是同一台机器上的同一套命令）。
  **教训：跨包比较 zip 字节数之前，先确认压缩器与级别相同**，否则又会把一个正常差异写成缺陷。
- **我在 `发布/0.4.0-rc4/说明.md` 的草稿里写了"分支 main 已推送"**——那时候还没推。
  这是上一轮"已推送"那句错话的**同一个坑第二次出现**。这次是在提交前自查发现的，
  改回"还没挂 Release"再推，推完才把状态写实。
  **规则要说死：分发状态那一段永远最后写，不许在动作完成前预填。**
- **同一个提交前自查又抓到一处日期写错**：我在四处新文档里写"验收清单已于 2026-10-29 补到 89 条"。
  `git log` 一查：那次提交是 **2026-10-28 09:25**，而 rc3 随包文本里那句"还没有一张对应的验收清单"
  提交于 **同一个早上 09:18**——**两件事只差七分钟，我却记成了隔一天**。
  这是本项目第三次日期归属出错（前两次见 `开发日志/2026-10-14.md`、`2026-10-20.md` 的更正段），
  根因同一个：**凭印象写日期，而不是先查 `git log`**。
  改法：凡写"某月某日做了 X"，先跑一次 `git log --format="%h %ad %s" --date=format:"%m-%d %H:%M" -S"关键字"`。
  **代价是真出了包的**：`变更日志.txt` 里那句"10 月 29 日补出来了"已经压进 zip，
  所以本包的 zip **重压过一次**（只有 `变更日志.txt` 变了，exe 与 `使用说明.txt` 逐字节未动，
  构建点仍是 `a9a1033`），两个新哈希见 `发布/0.4.0-rc4/说明.md`。
