# 第 4 轮（同日续）：登录、会话、收藏历史与设置页

## 做了什么

- **K-01 / K-02 关闭**：闸门新增 `IGateSink`，每次放行官方请求写一行（版本、接口标签、当日序号、本动作剩余预算），失败再写一行错误分类；当日计数按日期落 `daily.json` 并在启动时回填。实跑核对：日志里 5 行 = 5 次请求，重启后计数从 3 续到 5。
- **TASK-30**：`IOfficialSession` + `ProtectedSessionStore`（DPAPI CurrentUser → `session.protected`）。读取方法是数据层 internal，端口上没有任何返回 Cookie 的成员——这条由反射测试钉住。
- **TASK-29**：`OfficialLoginPage`（WebView2）+ `DomainGuard` 白名单 + 运行时缺失引导。实跑确认登录窗渲染出真实官方页，地址栏显示容器给出的 `kyfw.12306.cn`。
- **TASK-32**：收藏（≤20，不存日期）与历史（≤30，同 OD 同日只占一条）。
- **TASK-33 / 35**：设置与关于窗口（上限、码表日期与手动更新、登录状态与一键退出、清空本机数据带二次确认、版本号、再看声明）。
- **FR-18 补齐另一半**：码表手动更新（下载→校验条目下限→原子替换，失败保留旧表）。
- 107 个测试全绿、0 警告；合规与凭据自查两组 grep 全部通过。

## 做了什么决策

1. **不自动判定"登录成功了"**。官方登录标志字段没有依据，猜一个就是把不可见的判断塞进凭据路径。改成用户点"我登录好了"，界面措辞是"已取到登录状态（**尚未向官方验证**）"。
2. **数据层与测试工程改为 `net8.0-windows`**。DPAPI 只有 Windows 支持，与其逐处压 CA1416，不如让"这是 Windows 桌面件"体现在目标框架上。
3. **码表更新成功后提示"重启生效"**，不换内存索引。FR-22 明确允许"明确提示需重启"这一支。
4. **清空本机数据删整个自有目录**而不是逐个文件挑——漏一个就是"用户以为清了其实没清"。
5. **设置窗口复用 MainViewModel**。两个窗口各持一份状态就要写同步代码，而这个项目最不需要的就是那种复杂度。
6. **自查又抓到一处越界**：登录页里写死了官方站点字符串来读 Cookie。改成端口成员 `CookieScopeUrl` 由数据层给出——"能读哪一站的 Cookie"必须只有一个出处。

## 推迟了什么，为什么

**TASK-31 的中转解析没做，这是本轮唯一被主动推迟的功能。** `lcQuery` 游客态 302 到登录页是实测过的，但**登录态下返回什么结构一次都没拿到过**。写解析器就只能猜字段，而猜出来的换乘方案会直接变成亲友的购票决策依据——那是 NFR-18 与 AGENTS 七.5 明确禁止的事。所以本轮把不需要样本就能验证的部分（登录、会话附带、失效清除）全部做完，解析等一份真实样本。

**下一步拿样本的动作**：在验收时登录一次，把响应的字段名与结构（不含凭据）记进 `测试/接口样本/`，解析层与界面即可照样本补齐。

## 一句话教训

本轮三个缺陷（历史没落盘、设置窗口把"关于"整块切掉、写死的 Cookie 域名）里两个是**脚本改文件时静默没匹配上**造成的，一个是自查 grep 抓出来的。教训不是"别用脚本"，而是：**批量文本替换之后必须复查产物**，以及**自查清单要真的跑**而不是心里过一遍。

# 续：登录态第一次实测，结果是否定的

用户报告"已登录完成"后，我用采到的会话发了一次 `lcQuery`（一次请求，探针跑完即删）。

**结果：官方仍返回 302 → passport。** 采到的 Cookie 名单只有
`SF_cookie_2 / BIGipServerotn / BIGipServerpassport / uKey` 加三条界面偏好——**这是游客级的一套**，
没有业务会话。

**我这边确定的一个缺陷**：采集时只问了 `kyfw.12306.cn` 一站，登录身份那条很可能在 `www.12306.cn` 的域上被漏掉。
已改为端口给出 `CookieScopeUrls`（两个官方主机）、界面按名字取并集。

**另一个解释我没法排除**：用户当时可能没真正完成登录（页面右上角是否出现昵称这件事我没看到，
也不该由程序去看——那需要判断"什么算登录成功"，正是我不该猜的字段）。

**所以 TASK-31 仍然停在这里**，并且理由比之前更硬了：现在连"会话到底通不通"都还没确认，
更不可能写解析。已把这条否定证据写进 SPEC-007 第二节与 v1.8 变更记录——
否定结果同样是实测结论，不记下来下一轮就会以为登录已经通了。

## 第二次实测：并集采集之后仍然否定

用户按新流程重登并采集，**N 还是 7 条**，名单一字不差。带这套会话请求 `lcQuery` → 302 → passport；
换成中转页的 `Referer` + `API-Referer` 再试 → **同样 302**。用户确认内嵌页右上角已显示其用户名。

顺手做了一个不花任何网络请求的本地检查：WebView2 私有目录里**持久化**的 Cookie 只有 5 条
（3 条界面偏好 + 2 条 `_uab_collina`）。也就是说 `uKey`、`BIGipServer*`、`SF_cookie_2` 都是**会话级**的，
不落盘——浏览器进程一关就没了。这解释了为什么"采到的"和"官方登录页认的"能同时成立。

**结论**：问题不在采集漏了哪个字段，也不在请求头形态，而在于**业务会话是浏览器跟着
`passport` 那条 302 链走出来的**，而我们的客户端按设计不跟随重定向（SPEC-007 二节规则 4：
只跟随"接口改名"那一类）。

**两条路摆在这儿**：
- **A**：让用户在内嵌页里自己点进"中转换乘"页，再点"我登录好了"。握手由官方页面完成，
  我们只是在它之后读一次容器 Cookie——这是把 WebView 当浏览器用，不碰任何红线。
- **B**：让程序自己跟随 `passport` 的 302 链把会话跑出来。这跟 AGENTS 第五节第 2 条
  "禁止自行构造登录 HTTP 请求"挨得太近，**不该由我替用户决定**。

所以我停下来问，而不是先写出来再说。中转解析在拿到一次真实成功的样本之前继续不动。

## 第三次实测：解释 ① 成立，但真正的结论是"我们一开始就把路径读错了"

用户按新流程重登，采集从 7 条变成 **10 条**，新增的正是 `tk`、`JSESSIONID`、`_uab_collina`。
路径并集这个假设成立——那确实是我们自己的缺陷。

但带这套会话再请求，结果出乎意料：

| 请求 | 结果 |
|---|---|
| `GET /otn/lcQuery/query?...` | **HTTP 404**（不再是 302 到登录页） |
| `GET /otn/lcQuery/init`（中转页本身） | 仍 **302 → passport** |

**这说明 v1.1 那条"此接口需登录"很可能从头就是误判**：官方对不认识的路径先丢给登录墙，
于是"路径不对"被我们读成了"需要登录"。404 和 302 是两种不同的信号，之前没有区分过。

**我停在这里，没有继续试路径。** 每试一条就是向官方发一次请求，而"试"没有上界——
那正是频率红线要防的形态。真实路径与所需请求头改由用户自己浏览器的 Network 面板读一次取得：
零猜测、零额外请求。

## 探针顺手抓到的一个真缺陷

`QueryException` 只把技术细节放在 `Detail` 属性上，从没交给 `base(message)`。
而审计日志与本地日志记的都是 `ex.Message`——**于是每一条失败日志都只写着
"Exception of type ..."，等于没记**。已改为把细节拼进 Message 并加测试钉住。
这个缺陷只有在"真的去读一条日志"时才会暴露，而它恰恰是亲友报障时唯一的依据。

## 第四次实测：路径找到了，而且推翻了一条旧结论

用户从自己浏览器的 Network 面板读出真实请求，一次就定死三件事：
**路径是 `/lcquery/queryG`（不在 `/otn/` 下）**、参数名是 `*_telecode` 且 `purpose_codes=00`、
要把会话里的 `tk` 再作为同名请求头回传一次。

于是前面三次实测的所有矛盾都有了答案：`/otn/lcQuery/query` 的 404 是路径根本不存在；
`/otn/lcQuery/init` 的 302 是"那是页面不是接口"；我们采不到可用会话，是因为那个应用的
`JSESSIONID` 挂在 `/lcquery` 路径下，而采集范围里没有它。

**SPEC-007 v1.1 起写的"此接口需登录"从头就是误判**——官方对未知路径先丢给登录墙，
我们把"路径不对"读成了"需要登录"，并据此设计了整个中转功能。已就地更正（v1.12）。

## 拿到样本后解析层立刻抓出的两件事

1. **`all_lishi` 是"4小时18分钟"这种中文，不是 `hh:mm`**。按时间解析得到 0，
   逐字段核对的测试直接把它抓出来了。改成时长取 `all_lishi_minutes`、原文另存只用于显示。
2. **这个响应里没有 `yp_info_new`，官方根本不给票价**。所以 `Price` 一律 null、
   `PricesKnown` 恒为 false，界面那一格写"票价官方未给出"，也不按价格给中转方案排序。
   顺带：席别值里的 `--` 官方从未说明含义，按 `Unknown` 透传，不猜成无票。
