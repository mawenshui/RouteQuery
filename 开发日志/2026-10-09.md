# 晚些时候：新增"多买几站"（区间扩展）

## 用户要求

高峰期满票时"多买几站就有票"，要求列出需要多买的站、显示多花的金额、并支持 1–10 站的上限设置。

## 这个需求撞上了一条我自己写死的硬约束

SPEC-007 第四节是"**单动作 ≤3 次官方请求**"。而"多买几站"天生需要逐个候选区间各查一次——10 个候选就是 10 次。

我没有去改功能以适应约束，也没有默默绕开约束，而是**改了约束本身并说明代价**：请求预算按动作类型分级（基础 ≤3 不变，扩展 ≤10、硬上限 12），串行与 ≥3 秒间隔**不放宽**。同时补了一句审计口径——`RequestGate` 按动作类型分别计数写日志，发布前核对实际请求数。

留了一条明确的退出条件：如果实现阶段确认拿不到经停站序，FR-26 ~ FR-31 整体退回 V1.1，**不允许改成"用码表猜邻近站凑候选"**——那会产出一堆根本无法上车的方案，比没功能更坏。

## 主动收紧的三处（不是用户要求的）

| 收紧 | 原因 |
|---|---|
| 触发条件用 `canWebBuy`（列 11）而不是余票列 | Q-10 已经证明余票列互相矛盾。若用未确认列判定"这趟买不到"来触发，整个功能就建在一个已知错误的假设上 |
| **Δ 为负值判为解析异常**，不当正常数据显示 | 更长区间票价理论上不低于短区间。出现负数几乎必然是列位或席别对齐错了；照实显示会让用户按一个错数字决定多付钱 |
| 明确禁止自动下单/锁票，并写进不做清单 | 这个功能的产物恰好是"多花钱但有票的可下单方案列表"，离"替你买"只差一个按钮。价值越高的地方，红线越要提前钉 |

## 联动核对（用户明确要求做这一步）

逐条核对既有条目是否被改变，结论写进 PRD 6.10。最有价值的两条发现：

1. **FR-14 经停站钻取 P1 → P0**。它原来只是"想看就点开"，现在成了候选生成的唯一数据来源。
2. **Q-04 从"可以回避的未知项"变成"P0 阻塞项"**。v2.1 时它的处置是"降级为跳官方，不影响发布"；现在降级路径不存在了。**这是本次最重要的结构性影响**——一个新功能把一个被拖延的核实项变成了硬依赖。

还发现并消除了一处**规范自身的矛盾**：NFR-01 规定查询 ≤10 秒，而扩展批次天然 ≥30 秒。若不改，实现者为了满足界面指标会去压缩间隔或并发请求——**规范内部就在诱导违规**。已把时间承诺按动作类型拆成两类。

# 收尾：实测关闭 Q-04 / Q-10，并写完全部阶段文档

## 方法上的转折

前两次核实都在**猜列的语义**（v1.0 假设 `mapper`、v1.2 猜"列 34 可能是余票"），两次都错。这次换了办法：**下载官方自己的渲染脚本，读它把竖线串赋值给具名字段的那段代码**。

```
c9 = dc[da].split("|");
dd.train_no = c9[2];  dd.canWebBuy = c9[11];  dd.from_station_no = c9[16];
dd.wz_num = c9[26];   dd.ze_num = c9[30];  dd.zy_num = c9[31];  dd.swz_num = c9[32];
dd.yp_ex = c9[34];    dd.yp_info_new = c9[39];  dd.sale_time = c9[55];   ← 权威来源
```

一次就定论。**取值吻合不等于语义正确**——`90M0O0W0` 看起来太像余票串了，但它叫 `yp_ex`，跟余票没关系。

## 结论

| 未知项 | 结果 |
|---|---|
| **Q-04 经停站** | ✅ 端点是 `czxx/queryByTrainNo`（此前失败是**端点用错**，参数其实一致；日期需 `yyyy-MM-dd`）。**游客态可用**，K599 返回 32 站具名字段数组 |
| **Q-10 余票列** | ✅ **列 20–33** 是权威余票列；列 34 是 `yp_ex`，与余票无关——v1.2 记录的"两列矛盾"由此完全解释。并与页面 DOM **同瞬间逐格比对**：G6701 与 K599 共 8 项全部吻合（含 `rw_num=4` ↔ 软卧 4） |
| **Q-05 重复价格** | ✅ 列 39 解码与官方 `queryTicketPrice` 逐项一致（174/79/49、21.5/102.5/67.5），而官方只返回首条 → "取首条"由保守假设升格为**被验证的策略** |
| **Q-11 席别对齐** | ✅ 可对齐（按席别码为键）。同时发现：余票列名与票价席别码是**两套编码**，混用会让席别错位 |

**新发现的坑**：官方页面会用列 37/38 把"无票"渲染成**候补**。所以余票是三态，且**候补不能算有票**——否则"只看有票"会筛出一堆买不到的车。

## 按你的规定撤销了既有降级设计

用户要求"官方数据无法获取就报错，不要降级为其他方式获取的数据"。这条推翻了我自己前面的两处设计：

- 撤销 `API-04` 的"降级为跳转官方查看经停"；
- 撤销 v2.2 预留的"用码表猜邻近站凑候选"备选。

升级为硬约束 **NFR-18 数据来源单一性**，并回写 AGENTS.md 第七节。同时在设计里新增错误类型 **`DataUnavailable`**，与 `NoResult`（官方说没有，是有效信息）和 `ParseFailure`（结构变了，要新版本）严格三分——混成一个"查询失败"，用户就不知道该等、该重试还是该找我。

反思一句：这些"降级"当初是我为了让功能"不至于崩"而设计的，本质上是**用可用性名义掩盖取数失败**。在一个输出决策依据的工具里，那比功能不可用更危险。

## 顺带的取舍

确认**不使用 `API-06 queryTicketPrice`**：curl 直连被 302 到官方错误页、只在真实页面上下文可用，依赖它等于依赖"复刻浏览器流程"；而列 39 已实测与它一致。更重要的是——**这一条让"多买几站"的请求预算成立**：每个候选 1 次请求同时拿到余票与票价；若必须另取价，每候选变 2 次，≤12 的上限直接崩盘。

| 问题 | 决定 |

## 我主动指出的三处后果，而不是默默执行

1. **"默认开启检查更新"与 NFR-07 原文直接冲突**（原写"除官方接口外无任何第三方出站"）。我没有偷偷加功能，而是把规范改成一条**带六个条件的例外**：目标只限 GitHub、仅启动一次、请求不得含任何本机信息、可关闭、失败静默，并**明文禁止**借更新检查夹带配置下发/灰度/日志上传/远程控制。最后那条是我主动加的——一旦开了"远程能改应用行为"的口，个人工具就有控制端了，那是另一条线。
2. **"体积优先 + 不内嵌运行时 + 没有装机环境"三件事叠在一起的缺口**：老 Win10/精简系统可能没有 WebView2，登录与中转在那些机器上直接不可用。我把这个组合的后果讲清楚了，用户选择仍照原计划上。于是我的处理是**把它记成一次知情的风险接受**：RISK-19 不降级，`TC-F8`/`TC-U13` 在验收报告里显式写"未验证 + 无环境"。SPEC-005 第六节早就写过"不允许把未验证记成通过"——这条现在轮到我自己遵守。风险的实际承担者是亲友，而且出问题时你在现场、我不在。
3. **"学生/儿童票进 V1"这件事我没有直接做**：列 39 在同一席别下有第二条价格（`O=49.03`、`1=21.53`），而官方 `queryTicketPrice` **不返回**它，语义未确认。此时任何"这是儿童票/学生票"的标注都是猜，正好撞上用户上一轮刚定的 NFR-18。所以我在三个选项里把"只加中性说明、不算价"标为诚实做法，用户采纳。**这条不是我在替他减少工作量，而是数据不允许。**

# 2026-10-10：开始实现（第 0 轮 + 第 1 轮）

## 工具链先撞了一次

机器上只有 .NET **10** SDK，没有 8。第一反应是"技术栈决定 D-06 要推翻"，但没有先猜就先测：`net8.0-windows` 用 SDK 10 构建通过，且 `Microsoft.WindowsDesktop.App 8.0.29` 在机器上，能构建也能运行。**规范不用改**。同时发现 SDK 10 的 `dotnet new sln` 生成的是 `.slnx` 而不是 `.sln`，这一处确实要改规范（已改 AGENTS 与 SPEC-001 的文件名例外）。

## 第 0 轮：五项实测纠错（没写一行代码就值回票价）

用 8 次真实请求（串行、每次间隔 4 秒）拿到 246 条记录，纠正了五处会咬人的设计错误：

| 我原本写的 | 实际是 | 后果如果没测 |
|---|---|---|
| 车次号自检 `^[GDCZTKLY]\d{1,4}$` | 存在纯数字车次（`1461`） | **整批普速列车被判解析失败**，用户看到"某天的车次凭空少了一半"且无任何提示 |
| `canWebBuy` 取值 Y/N | 还有 `IS_TIME_NOT_BUY` | 同上，所有"尚未开售"车次连带整批失败 |
| 列 34 `*` 当作某种余票状态 | `*` 只在未开售行出现；未开售另有"整行全空"表现 | 把"没开售"显示成"无票"，用户会放弃本来能抢的车 |
| 候补由列 37/38 判定 | 列 37 是**车次级**（97/122 为 1，其中 48 仍有票），官方判定式是"值==无 且 席别非 WZ_/QT_ 且 列37==1"，列 38 只管颜色 | "只看有票"会把大量有票车次筛掉 |
| 预售期未测 | 含当天 15 天；且**越界响应与风控拒绝同形**（都是 HTML 错误页） | 日期越界会被显示成"官方暂时不可用"，用户反复重试而问题永不自愈 |

顺带用官方带参 URL 关闭了 Q-07。

## 第 1 轮：离线可测部分，59 个测试全绿

写了模型、8 类错误、端口、两张布局表、结构自检、解析器、票价解码、余票四态、码表加载与索引、预售期窗口、扩展候选生成、差额计算。构建 0 警告。

**测试抓到一个真实缺陷**：`ColumnSpec` 用静态 `Dictionary` 缓存编译后的正则，xUnit 并行执行时直接抛 `InvalidOperationException`（集合状态被并发写损坏）。改成 `ConcurrentDictionary`。这种 bug 评审看不出来，跑一遍也不会错——只有在并行下才炸，而 WPF 里并发解析是真实场景。

**审计抓到我自己的规则有漏洞**：SPEC-004 说"下标只允许出现在布局表一处"，但 `StationNameLoader` 里的 `f[1]`…`f[7]` 完全合规地绕过了它——因为码表不是"API-02 的响应"。我没放宽规则，而是**给码表也建了一张字段布局表**，并把规则改写为适用于"所有位置式格式"。规则的适用对象写窄了，就等于没写。

另一处：URL 的 grep 检查会被 XAML 的 `xmlns` 全部命中。一个总是误报的检查等于没有检查，所以口径必须限定在 `.cs`。

## 现在能做什么、不能做什么

- **能**：解析一份真实响应成强类型结果（含票价、四态余票、放票时间），官方改字段时立刻判 `ParseFailure` 并整批停手；码表 3404 条离线可用并支持中文/拼音/简拼匹配与同城聚合。
- **不能**：还没写 HTTP 层，所以**目前发不出真实查询**。这是第 1 轮的既定边界（判据本就是"离线可测部分测透"）。
