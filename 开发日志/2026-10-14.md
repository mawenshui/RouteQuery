# 开发日志 2026-10-14

本轮只做一件事：把 FR-38（浅色系渐变皮肤）从需求落到能交给亲友看的程度，
并且给它配上**能自己证明自己没坏**的守卫。Core 与 Data 一行没动。

## 一、先说清楚我为什么要在测试里画像素

上一轮结束时的处境：皮肤改完，244 个测试全绿，但我**一次都没看见它长什么样**。
这台机器的窗口置不到前台（`activate_window` 报"could not be made foreground"，
截出来的客户区是一片白），所以"我看过界面"这句话当时是说不出口的——
而一条"界面改好了"的进展如果只能靠我自己看，那它对下一轮的我等于不存在。

于是换了个思路：**渲染不依赖窗口显示**。测试里把主窗口的内容挂到一个固定尺寸的宿主上，
用 `RenderTargetBitmap` 画到内存，再存成 PNG。这样两件事同时成立：
我能真的看见它，而且"画出来了没有"变成一条可以重复跑的断言。

代价是三个坑，都记在这里：

1. **没 Show 的 Window 画不出自己的背景**。`Window.Background` 不在内容的可视树里，
   渲出来四周缺一圈底。解法是把同一支画刷（从 `window.Background` 读，不复制键名）
   挂到宿主 `Border` 上。
2. **把内容从 Window 里摘出来，`DataContext` 就断了**。继承链一断，界面变成没有数据的空壳——
   第一版渲染图里出发/到达框全空、下拉框没有选中项，就是这么来的。
   这一条值得写进日志：静态检查与单元测试都发现不了"我测的是个空壳"，只有图能看出来。
3. **数颜色的门槛不能凭感觉定**。我先把门槛调成一个必然大失败的数，
   把四种视图的真实数字打出来看（前景像素 3.0~3.6 万，窗口底竖线 8~16 种色），再回头定门槛。

## 二、渲染图当场揪出的一个真缺陷：折叠面板的标题变成了一串字面量

浅色档第一张图底部明明白白写着 `Content="{TemplateBinding Header}"`。
原因很低级：`主题.xaml` 里 Expander 模板那行 `Content="…"` 换行时落在了开始标签的 `>` 之后，
于是它不再是属性，而是 ToggleButton 的**元素内容**——XAML 照单全收，把它当字符串画了出来。
编译过、解析过、样式套上过，三层守卫全绿，只有像素看得见。

顺带修的第二处：`{TemplateBinding Header}` 本身也是错的，那层的 TemplatedParent 是 ToggleButton，
它没有 Header 属性。改成 `{Binding Header, RelativeSource={RelativeSource TemplatedParent}}`。

## 三、守卫分三层，每层各挡一种"看起来成功了"

- **静态层**（`ThemeGuardTests` 新增 5 条）：两档色板的渐变键必须一一对应；每个渐变至少两个色标
  （只有一个色标的是假渐变）；方向必须全部纵向同向；正文色与次级色对**所在底的两端分别**过 AA；
  数据区行底渐变两端亮度差压到 ≤0.04；控件边界对底 ≥3:1。
- **模板层**（`SkinRuntimeGuardTests` 前半，28 例）：14 个换肤控件在两档色板下各建一次，
  真的套样式、真的开弹层。挡的是"触发器只在第一次应用模板时才构造"这类错——
  上一轮 DatePicker 把主窗口炸没，编译与静态守卫当时都是绿的。
- **像素层**（同文件后半，8 例）：直达 / 中转 / 报错 / 设置四个界面 × 两档色板，
  判三条：整幅不是空白、窗口底那一列不是纯色、跟底色差得远的像素不能是零。
  每次跑还往 `%TEMP%\rq-skin-render\` 落 8 张 PNG 供人复核。

**三条都做了"种错验证"**（不验证的守卫等于没有守卫）：
把窗口底换成 `Brushes.White` → 报"渐变没画出来"；把内容换成 null → 报"根本没渲染出来"；
把浅色档正文色改成接近底色 → 前景像素从 3.0 万掉到 2.0 万，**没有跌破门槛**。
最后这一条我没修饰：它说明像素层兜不住"某一支笔刷撞色"，那种精度归静态层管
（它能指到具体哪一支刷、哪一端）。像素层只兜"整片一个字都没画出来"。门槛注释里写的就是这个实测数。

## 六、另一件事：装了 skillhub 商店和 `dev-expert` skill

用户要求按 `https://skillhub.cn/install/skillhub.md` 装商店，再装 `@indiv-ebandao/dev-expert`。
没有直接 `curl | bash`——先把 kit 包下载解压、读了源码，几个发现决定了最终怎么装：

- 那份安装脚本是给 **OpenClaw** 写的：默认把商店 skill 装到 `~/.openclaw/workspace/skills/`，再调 `openclaw config set plugins...`。本机根本没有 `~/.openclaw`，Qoder 读的是 `~/.qoder/skills` 与 `~/.agents/skills`——照文档全量装，商店那半截会落进一个没人读的目录。
- 脚本硬性要求 `python3`，本机只有 `python.exe` 3.14，默认模式会报"python3 is required"直接退出。
- 默认往 `~/.skillhub/config.json` 写 `self_update_url` 且开启自动自升级：CLI 每次启动可能静默拉远程 `latest.tar.gz` 覆盖自身代码。
- 默认还装两个 `SKILL.md` 行为策略（"highest-priority""MUST trigger""优先 skillhub"），会跨项目改变以后每一次会话。

按选定的最小方案落地：只从审过的本地文件手工装 CLI 到 `~/.skillhub` 与 `~/.local/bin/skillhub`，`config.json` 里 `auto_self_upgrade=false`、`install_workspace_skills=false`，不装策略 skill、不动 OpenClaw 插件、不起 gateway。wrapper 做了 `python3 → python` 回退；另外 Windows GBK 控制台在打印 `✓` 时会抛 `UnicodeEncodeError`（安装本身已经完成），跑 CLI 需带 `PYTHONUTF8=1`。

`dev-expert` v2.1.0 先下到临时目录审完 86 个文件才放。干净的部分：29 个钩子脚本全是本地正则扫描器，逐个 grep 过，**没有任何网络出口**，也不读凭据。有风险的部分：它的 Step 0.5 会推着未来的 agent 去跑 `init_deploy.py --apply`，把 26 条在每次 Write/Edit/Bash 触发的钩子注册进 `.claude/`、`.codebuddy/`、`.trae/` 等配置，`--scope user` 时影响本机所有项目；它的记忆协议还要往仓库根写 `.ai-memory/`、`project_memory.md`、`_plan.md`。这跟第三节"根目录只允许三个文件"和第四节五道门禁是正面冲突。

用户选"原样安装 + 落项目级压制说明"：包完整装在 `~/.agents/skills/@indiv-ebandao/dev-expert`（Qoder 已识别到 `dev-expert`），同时新增 **AGENTS.md 第十节**，把外部 skill 明确压在本文件之下，并禁止在本仓库部署钩子、禁止写入那些过程文件。

**遗留**：第十节只管得住本仓库；这个 skill 在其它项目里被触发时仍可能自行部署钩子，要全局压制得在用户级规则里另写一条。自动升级是关着的，以后更新要手工重跑 `skillhub install`，届时应把新包重新审一遍。

## 七、出 rc5 试用包：把"发亲友"这件事写成可核对的四个动作

用户点头之后推了 `main`（`a9860d9..c39ad3c`），然后按 SPEC-006 v1.3 出 `0.3.0-rc5`。
这一轮的重点不是压包，而是**把"受控试用"从一句态度变成四条能核对的东西**：

- **顺序照 rc4 的教训来**：先提交 `<Version>` 与发布文档（`d03ab8a`），再从这棵树 publish，
  然后逐字核对 exe 的 `ProductVersion` = `0.3.0-rc5+d03ab8aa138d…`。
  上一版第一次打包时版本号还没提交，戳落在上一个提交上——自己刚写进文档的"可核对性"，
  下一版就不能靠印象。
- **① 第一屏试用声明**写进 `使用说明.md` 的开头，四句齐全：试用件、未走完整验收、
  **不要拿它显示的时间或价格决定买哪趟票**、有问题把日志发回。
- **② 试用名单**在 `发布/0.3.0-rc5/说明.md` 里做成一张空表（收件人 / 关系 / 哪天以什么方式告知 /
  版本 / 校验和前 8 位 / 反馈）。**表是空的，这一点不修饰**：只有你能填，
  而"我发给你了"和"你同意了"是两件事，要记的是后者。
- **③ 反馈路径**固定为日志文件，并明写"不用截图、不用描述"。
- **④** 说明.md 里显式写着"本包不是验收，`v1.0.0` 仍要第四节清单全打勾"，也显式写着**没挂 Release**。

两份随包 txt 仍由 md 生成（脚本还没进仓库，见遗留）。生成后跑一遍禁词断言：
`FR-` / `TASK-` / `K-0x` / `SPEC-` / `commit` / 反引号 / 表格线，命中就不出包——
这是防 rc3 那次"包内 `变更日志.txt` 停在 rc2 还带内部编号"的事故重演。

**生成脚本自己有个坑值得记**：第一版把 `#` 记号在 `>` 之前剥，于是引用块里的
`> ## 先读这一段` 变成裸的 `## 先读这一段`——正好是这份文件最该被读到的一行。
改成先剥引用符再剥标题记号。**"从 A 生成 B"的脚本，错也一定是成批错的。**

包：`RouteQuery-0.3.0-rc5-win-x64.zip`，68,164,727 字节（约 65.0 MiB，NFR 100 MB 内），
四个 SHA-256 全记进说明.md。冒烟：从包里单独取 exe 放空目录，起来稳定 30 秒后干净结束，
当日日志零新增未处理异常。

**遗留**：① 整条 `publish → 转文本 → 压包 → 算校验和 → 回填说明` 仍未一键化，
生成脚本也还没进仓库（它现在只活在我的命令行里，下一轮的我等于又要重写一遍——这本身就是 rc3 那类"手工副本会漂"的形态）；
② 外观的肉眼验收一条没过（三档缩放、真实文案换行、登录那一屏）；③ Release 挂不挂等你说。
