# 开发日志 2026-10-14

本轮只做一件事：把 FR-38（浅色系渐变皮肤）从需求落到能交给亲友看的程度，
并且给它配上**能自己证明自己没坏**的守卫。Core 与 Data 一行没动。

## 一、先说清楚我为什么要在测试里画像素

上一轮结束时的处境：皮肤改完，244 个测试全绿，但我**一次都没看见它长什么样**。
这台机器的窗口置不到前台（`activate_window` 报"could not be made foreground"，
截出来的客户区是一片白），所以"我看过界面"这句话当时是说不出口的——
而一条"界面改好了"的进展如果只能靠我自己看，那它对下一轮的我等于不存在。

于是换了个思路：**渲染不依赖窗口显示**。测试里把主窗口的内容挂到一个固定尺寸的宿主上，
用 `RenderTargetBitmap` 画到内存，再存成 PNG。这样两件事同时成立：
我能真的看见它，而且"画出来了没有"变成一条可以重复跑的断言。

代价是三个坑，都记在这里：

1. **没 Show 的 Window 画不出自己的背景**。`Window.Background` 不在内容的可视树里，
   渲出来四周缺一圈底。解法是把同一支画刷（从 `window.Background` 读，不复制键名）
   挂到宿主 `Border` 上。
2. **把内容从 Window 里摘出来，`DataContext` 就断了**。继承链一断，界面变成没有数据的空壳——
   第一版渲染图里出发/到达框全空、下拉框没有选中项，就是这么来的。
   这一条值得写进日志：静态检查与单元测试都发现不了"我测的是个空壳"，只有图能看出来。
3. **数颜色的门槛不能凭感觉定**。我先把门槛调成一个必然大失败的数，
   把四种视图的真实数字打出来看（前景像素 3.0~3.6 万，窗口底竖线 8~16 种色），再回头定门槛。

## 二、渲染图当场揪出的一个真缺陷：折叠面板的标题变成了一串字面量

浅色档第一张图底部明明白白写着 `Content="{TemplateBinding Header}"`。
原因很低级：`主题.xaml` 里 Expander 模板那行 `Content="…"` 换行时落在了开始标签的 `>` 之后，
于是它不再是属性，而是 ToggleButton 的**元素内容**——XAML 照单全收，把它当字符串画了出来。
编译过、解析过、样式套上过，三层守卫全绿，只有像素看得见。

顺带修的第二处：`{TemplateBinding Header}` 本身也是错的，那层的 TemplatedParent 是 ToggleButton，
它没有 Header 属性。改成 `{Binding Header, RelativeSource={RelativeSource TemplatedParent}}`。

## 三、守卫分三层，每层各挡一种"看起来成功了"

- **静态层**（`ThemeGuardTests` 新增 5 条）：两档色板的渐变键必须一一对应；每个渐变至少两个色标
  （只有一个色标的是假渐变）；方向必须全部纵向同向；正文色与次级色对**所在底的两端分别**过 AA；
  数据区行底渐变两端亮度差压到 ≤0.04；控件边界对底 ≥3:1。
- **模板层**（`SkinRuntimeGuardTests` 前半，28 例）：14 个换肤控件在两档色板下各建一次，
  真的套样式、真的开弹层。挡的是"触发器只在第一次应用模板时才构造"这类错——
  上一轮 DatePicker 把主窗口炸没，编译与静态守卫当时都是绿的。
- **像素层**（同文件后半，8 例）：直达 / 中转 / 报错 / 设置四个界面 × 两档色板，
  判三条：整幅不是空白、窗口底那一列不是纯色、跟底色差得远的像素不能是零。
  每次跑还往 `%TEMP%\rq-skin-render\` 落 8 张 PNG 供人复核。

**三条都做了"种错验证"**（不验证的守卫等于没有守卫）：
把窗口底换成 `Brushes.White` → 报"渐变没画出来"；把内容换成 null → 报"根本没渲染出来"；
把浅色档正文色改成接近底色 → 前景像素从 3.0 万掉到 2.0 万，**没有跌破门槛**。
最后这一条我没修饰：它说明像素层兜不住"某一支笔刷撞色"，那种精度归静态层管
（它能指到具体哪一支刷、哪一端）。像素层只兜"整片一个字都没画出来"。门槛注释里写的就是这个实测数。

## 七、出 rc5 试用包：把"发亲友"这件事写成可核对的四个动作

用户点头之后推了 `main`（`a9860d9..c39ad3c`），然后按 SPEC-006 v1.3 出 `0.3.0-rc5`。
这一轮的重点不是压包，而是**把"受控试用"从一句态度变成四条能核对的东西**：

  然后逐字核对 exe 的 `ProductVersion` = `0.3.0-rc5+d03ab8aa138d…`。
  上一版第一次打包时版本号还没提交，戳落在上一个提交上——自己刚写进文档的"可核对性"，
  下一版就不能靠印象。
- **① 第一屏试用声明**写进 `使用说明.md` 的开头，四句齐全：试用件、未走完整验收、
  **不要拿它显示的时间或价格决定买哪趟票**、有问题把日志发回。

  而"我发给你了"和"你同意了"是两件事，要记的是后者。
- **③ 反馈路径**固定为日志文件，并明写"不用截图、不用描述"。
- **④** 说明.md 里显式写着"本包不是验收，`v1.0.0` 仍要第四节清单全打勾"，也显式写着**没挂 Release**。

两份随包 txt 仍由 md 生成（脚本还没进仓库，见遗留）。生成后跑一遍禁词断言：
`FR-` / `TASK-` / `K-0x` / `SPEC-` / `commit` / 反引号 / 表格线，命中就不出包——
这是防 rc3 那次"包内 `变更日志.txt` 停在 rc2 还带内部编号"的事故重演。

**生成脚本自己有个坑值得记**：第一版把 `#` 记号在 `>` 之前剥，于是引用块里的
`> ## 先读这一段` 变成裸的 `## 先读这一段`——正好是这份文件最该被读到的一行。
改成先剥引用符再剥标题记号。**"从 A 生成 B"的脚本，错也一定是成批错的。**

**这一轮最该记下来的是排错过程，不是功能本身。**

主窗口改完之后编译报 `MC3074：XML 命名空间里不存在标记"Window"`，行 1 列 9。这句话完全没指到现场，
而我按它字面意思找了很久——文件是好的、命名空间是对的、XML 是平衡的。中间走过的弯路值得写下来防重演：

- 我先怀疑 `x:Name` 加在 `RowDefinition` / `ColumnDefinition` 上（它们不是 FrameworkElement，不生成字段）→ 改成从宿主 Grid 取，仍报错；
- 再怀疑中文标识符 → 换成 ASCII，仍报错（**这一步之后我的"仍报错"其实已经被污染了**：一次还原操作把旧副本盖了回来，
  于是 XAML 里是中文名、代码里是 ASCII 名，两边不一致，报的正是我一开始就排除掉的那类错）；
- 又把整份文件按块二分：去掉菜单、去掉列表模板、去掉详情区、去掉分隔器——**每一次都"仍报错"**，
  因为每次还原都把我自己刚改对的东西又盖回去了；
- 最后用一个只含命名元素的最小 XAML 顶上去编译，错误立刻变成一条精确的 `CS0272：set 访问器不可访问`。
  到这一步才看清：**MC3074 是 C# 编译失败的级联表现，它根本不指向 XAML。**

真正的错误有两个，都很普通：视图模型里 `StationUpdateNeedsRestart { get; private set; }` 被界面写了；
以及一次 `cp` 还原把命名改动的两半拆开了。修法也普通：给视图模型加一个 `AcknowledgeStationUpdate()`，
让"问过用户了"这件事由拥有该状态的一方说出口。

**教训两条**：① WPF 里 `MC30xx` 报在 XAML 根元素上时，先怀疑代码后置，用一个最小 XAML 换掉现场再判；
② 二分排错时每一步都要能确认"我现在测的就是我以为的那个文件"——我那次是**自己把修复回滚了还继续往下猜**，
白白烧掉了十几轮编译。二分的前提是状态可信，状态不可信时先停下来把还原路径写死（本轮之后我把工作副本留在 `D:/tmp/final.xaml`）。

## 九、七项落地时各自定死了什么

- **表头**：不新增排序语义，只把 FR-12 已有的五个键映射到四列，且**点表头只改下拉那一份状态**（两处各存一份就会出现"表头显示 ▴ 而实际按另一键排"）。
  表头画在 `ScrollViewer` 外面而不是用 `GridView`——后者的列宽不支持 `*`，而席别那一列必须吃掉剩余宽度，否则 FR-09"首屏不横向滚动"就破了。
  列宽两处各写一遍一定会漂，所以配了一条守卫逐列比对，种一像素的错就判红。
- **选中即取**：额度消耗从"点按钮"挪到"点行"，所以"今日还可查询 N 次"从加载态提升为常驻；
  同一趟取过不再取（缓存挂在行视图模型上，天然按"这一趟 + 这一次查询"生效，不会跨日期复用）；
  换选作废在途请求；**详情区被隐藏时干脆不取**，此时点行上的按钮会先把面板显示出来。
  没有加任何去抖定时器——那是 TASK-43 立的"应用内不存在定时器"的反面，也是守卫会判红的东西。
- **自动匹配**：只认"站名完全相同"与"候选恰好一条"，其余一律不选。
  顺手修了一处不一致：`PickFrom` 以前只写 `_from` 不写 `_fromPick`，自动选定后候选列表的高亮与实际用于查询的站不是一个对象。
- **显隐与分隔器**：不进设置页、不持久化。`Expander` 因此被换掉（它要 Auto 行高，与像素行高的分隔器相冲），
  样式和它的运行时守卫用例一并删除——不留没人用的样式。
- **浅色加深**：第一版行底两端亮度差算出 **0.044**，被 FR-38 那条"≤0.04"判红。
  我没有去改门槛，而是把行底两端收窄到 0.038 才通过。**这一条是规范拦住了实现**，值得记：
  门槛如果每次都能在失败时说服自己改它，它就等于不存在。

**遗留**：`0.4.0-rc1` 只升了版本号，包没出——TASK-66 的肉眼走查在前；
菜单、表头、分隔器这三处新表面在 125%/150% 下没看过；`MainWindow.xaml` 经过这次拼装，
缩进有两处不齐（新块沿用了旧层级），下次改动时顺手理平，不单独提交一次纯格式改动。

## 十一、第 10 轮：先去看了一眼官方页面，再动手

原因是第 5 条——"同样是 G3，官网的坐席和价格比应用齐全"。这句话有两种完全不同的成因：
**一种是显示策略在丢数据，一种是数据层根本没解析出来**。
不分清就动手，很可能去补一堆本来就在的字段，或者更糟：为了"看起来齐全"给没证据的列贴标签。

读到的事实（北京南→上海 2026-10-15 的 G3）：

- 官方席别列头依次是 商务座/特等座、**优选一等座**、一等座、二等座/二等包座、高级软卧、
  软卧/动卧/一等卧、硬卧/二等卧、软座、硬座、无座、其他；
- 同一行各单元格的 DOM id 前缀依次是 `SWZ_` `GG_` `ZY_` `ZE_` `GR_` `RW_` `YW_` `RZ_` `YZ_` `WZ_` `QT_`，
  值是 12 / 候补 / 候补 / 有 / -- / -- / -- / -- / -- / 有 / --；
- 同一行票价串解出 商务 2337.00、一等 1069.00、二等 667.00，第二条 `O` 记录是 667.03——
  又一次印证"同席别取首条"是官方自己也在用的策略。

结论有两条。**一条是我们的数据一直都在**：`SeatTexts.Summary` 写死了"取前 3 个"，
官方给五个席别五个价，界面只摆三个还不带价——用户看到的"不齐全"就是这么来的。
**另一条是列 20 的中文标签我们一直标错了**：`gg_num` 就是"优选一等座"，
而它在我们代码里叫 `Unknown20`、在界面上显示成"未确认席别"。

于是这一轮第一次破了"`Core/` 与 `Data/` 零改动"的例：把枚举成员改名、把列来源标成"观察确认"，
并把票价短码 `A` 从"一等座"改挂到"优选一等座"——同一个短码在中文名表和余票映射表里说两种话，
是价格错挂到别的席别上的现成路径。破例写进了计划的进度行，没有悄悄做过：
**一个已经被证伪的名字留在代码里，比多改两行更贵**。

`yb_num`（列 27）与 `srrb_num`（列 33）官方在这一行没有给展示列，**继续写"未确认席别"**。
没有证据就不贴标签，这条不因"看起来应该差不多"而松动。

## 十二、反馈的位置：话说了，但说的地方不是用户眼睛在的地方

第 1、2 条截图是同一类毛病：**"这个日期没有直达车次"显示在窗口顶部，而用户看的是中间那块表；
"收藏已满 20 条"写在左下角一行小灰字，而用户刚点的按钮在右上角。**
这不是措辞问题，也不是样式问题——话是对的，位置让它等于没说。

所以 FR-46 定的不是"更好看的提示框"，而是一条位置规则：**反馈出现在引发它的动作所在的区域里**，
顶部只留一句"当前状态"。四级（结果/提示/警示/错误）共用一个组件形态，级别只换底色与文字色。

实现上有一个取舍值得记：级别**由文案键判定**（`LevelOf(text)` 拿这句话与几条警示/错误文案比），
而不是在二十个赋值点各记一遍"这条是警示"。后者一定会漏一处，而漏掉的那处正好是小灰字显示错误信息——
也就是这次反馈里最没用的那种形态。

`DetailHint` 顺手从"不通知的自动属性"改成会通知的：它以前填上经停表之后内容变了界面却不知道，
反馈条要按它决定显示与样式，这个老问题就藏不住了。

**这一轮的守卫**：多一个设置入口、反馈条少一级底色、席别又只取三个——三处各种了一遍违例，全部判红。
测试 270 → **273 全绿，0 警告**。渲染图复核了两处容易出错的挪动：额度紧贴查询按钮、
"共 x 趟车"落在表上方（第一版它压在表头"操作"两个字上，是看图才发现的）。

## 十三、自动化验证跑出来的不是"显示不全"，是"价格挂错席别"

用户授权"改进完成后可以全自动操控浏览器和应用做查询、测试、验证，但注意频率"。
跑完这一轮，最要紧的产出不在界面上，而在数据层——**FR-49 那批改动其实只修好了一半**。

### 先说验证本身（合计 3 次官方查询 + 1 次官方页面加载）

应用侧：北京南→上海 2026-10-14，一次查询出 16 趟，日额度 51 → 46。
选中 G25 即出经停表（FR-43 达成），表头常驻、"共 16 趟车"只在表上方出现一次。
官方侧：同一 OD、同一日期加载一次结果页，把 16 行的 `yp_info_new` 与每个席别单元格的
`aria-label` 整批读出来对照。**没有点任何购票相关的东西，没有第二次翻页请求。**

### 然后是对不上的地方

官方页面 G25 那一行的 `aria-label` 是逐格写好的：
"商务座票价2315元，余票候补""一等座票价1058元""二等座票价661元，余票2""无座票价661元，余票有"。
应用给的是：商务 2315 ✓、一等 1058 ✓、二等 661 ✓，**无座"官方未给出票价" ✗、优选一等座"官方未给出票价" ✗**。

席别条数已经和官方一模一样了，价格却少两档——问题只能在"哪条价格属于哪个席别"这一步。

### 追到两处结构性错误

顺着 DOM 往上找到官方页面自己维护的两张表：

- `window.seatTypeCodeForName`：`3`=硬卧、`4`=软卧、`D`=**优选一等座**、`A`=高级动卧、`P`=特等座、`J`=二等卧、`F`=动卧。
- `queryLeftTicket_end_js.js` 里生成 `aria-label` 的那个函数：切分写得很明白
  `c9=dc.substring(0,1); df=dc.substring(1,6)/10; de=dc.substring(6,10)`，
  也就是 **短码(1) + 角(5) + 尾部(4)**；而无座那一支是 `if("WZ_"==di){if(de>=3000){…}}`——
  **官方判无座只看尾部 ≥3000，根本不看短码**。

对照我们的实现：切分用的是 `短码(1) + 分(6) + 附加(3)`，短码表里 `3`/`4` 互换、`D` 记成二等卧、
`J` 记成二等座、`A` 记成优选一等座、`P` 记成动卧、`F` 记成观光座，还有一个官方不存在的 `T`。

错误切分的直接后果：`O066103062` 被读成"661.03"，看起来就是二等座 661.00 的重复记录，
于是"同席别取首条"把它整条丢掉——无座永远没有价。而真正的伤害在短码表那边：
**K599 的硬卧被标成 102.5、软卧被标成 67.5，一个比软卧还贵的硬卧**，摆在界面上与真数据毫无区别。

### 为什么这份证据 2026-10-09 就在仓库里，却没人读出它

`测试/接口样本/queryTicketPrice-票价样本.json` 早就写着 K599 `"3":"675"`、`"4":"1025"`、`"WZ":"¥21.5"`。
按官方表这就是硬卧 67.5、软卧 102.5、无座 21.5——**样本本身就否掉了当时写下的"次条官方不展示"**。
但那条记录被写成"1/4/3 首条与官方一致（21.5 / 102.5 / 67.5）"，顺序读成了"硬座/硬卧/软卧"，
于是 `3`=硬卧 这个错就顺着文档、代码注释、测试断言一路传了下来，测试还全绿。

**根因不是没查官方，是查完之后只做了逐条抽查。** 错误切分是自洽的：
每条记录单独看都对得上，只有"尾部余票数 == 该席别那一列的取值"这种横跨整行的关系才能把它问住。
所以这次补的守卫不是又一条断言，而是一条不变量：拿两份真实样本、29 条可比对记录逐条验，
再把 `3`/`4` 故意互换跑一遍——它报了"K599 短码 4 尾部 2 → HardSleeper 那一列实际是 有，不是 2"。
旧表在同样判据下 22 条里 11 条矛盾。

### 顺手改掉的两处

- 顶部信息条还在重复"共 16 趟车"（表上方已经有一句）。现在顶部只说"查询完成，结果见下方车次列表"，
  零趟与筛选后空也一并交给结果区的覆盖层说——同一句话说两遍，用户读到的是回声不是反馈。
  官方给零趟原本有一条单独的分支，现在删掉了，跟"有十几趟"走同一条刷新路径。
- 渲染用例加了两例"直达空态"（浅色/深色）。空态是覆盖层，断言只能证明"画了"，
  落点对不对靠 `%TEMP%\rq-skin-render` 里那张图——图上那句话正好在直达区域正中。

### 遗留

- `yb_num`（列 27）、`srrb_num`（列 33）仍未确认；官方把动卧（短码 `F`）对齐到 `SRRB_` 列，
  也就是说列 33 很可能就是动卧，但**没有 DOM 列头证据就不改名**，`F` 的价格继续不对齐。
- 余票是实时变的：15:57 官方页面 G25 优选一等是"候补"，16:15 应用里是"有"。
  这类差异不能算 bug，也不能拿它当"我们和官方一致"的证据——**核对只能在同一时刻的两侧快照之间做**，
  这条已经写进 FR-49 的验收①。
- 收藏满的提示（FR-47 的另一半）需要把收藏填满才能看到，本轮没有制造这个状态，留给肉眼走查。
- 测试 273 → **276 全绿，0 警告**（新增一条不变量守卫 + 两例“直达空态”渲染）。`0.4.0-rc2` 包**还没出**，等用户点头。

## 十四、出 0.4.0-rc2 包：一条既有缺陷是在翻日志时撞出来的

按 SPEC-006 的老顺序走：**发布文档先行 → 提交 → 从干净树 publish → 转文本 → 压包 → 算校验和 → 冒烟**。
构建点 `f8a3ed1`，exe 内嵌 `ProductVersion = 0.4.0-rc2+f8a3ed19ffd…`，逐字核对过。
包 68,171,889 字节（约 65.0 MiB，在 100 MB 上限内）。

两份 txt 仍由 md 生成、不手工维护，禁词断言（`FR-` / `TASK-` / `K-0x` / `SPEC-` / `commit` / 反引号 / 表格线 / `#`）
**第一次跑就命中了**：使用说明里那句"先读这一段"是写在引用块里的小标题（`> ## …`），
转换器只剥了 `> ` 没剥 `## `，于是 `#` 漏进正文。改转换器而不是改文档——
第一屏那段话是给亲友看的，不该为了迁就脚本把它降成普通段落。

冒烟：空目录里起来、稳定 32 秒，当日日志**一行都没多**（既没请求也没异常）。
这条"零新增"本身就是判据：它证明启动路径不碰官方接口。

### 撞出来的那条

翻同一份日志时看到 14:58 两条 **未处理异常**（版本头 `v0.4.0-rc1`）：

```
InvalidOperationException: … requires an element of type 'Object', but the target element has type 'String'.
   at RouteQuery.Data.Parsing.TransferParser.Parse(...)
   at RouteQuery.App.ViewModels.MainViewModel.RunTransferAsync(...)
```

`TransferParser` 遇到"某段是字符串而不是对象"时直接抛，异常穿过 `AsyncCommand` 落到 WPF 分发器。
**这是全应用唯一一条没有降级路径的解析入口**，正面违反 AGENTS 第七节"所有网络调用必须有超时、取消、
失败降级三件套"。它跟本轮改动无关（不同接口、不同文件），所以**没有塞进 rc2**——

已记进 `发布/0.4.0-rc2/说明.md` 的已知问题，不留在对话里。

顺带一条从日志读出来的事实：**一次普通查询发的是 2 个请求**（`API-01 会话` + `API-02 余票`），
所以额度每次掉 2。这解释了前面看到的"51 → 49"，不是重复计数。

## 十五、拆掉那条崩溃：一个 `TryGetProperty` 的三类后果

用户定了顺序：**名单不填 → 先修崩溃 → 再推 GitHub**。

### 崩溃的形状

日志里三条一模一样：合法 JSON 响应，官方把 `data` 给成一段文字，而代码直接
`data.TryGetProperty("middleList", ...)`。`TryGetProperty` 只对**对象**合法，
于是抛 `InvalidOperationException`——它不是 `QueryException`，界面那套"按类别取人话文案"的机制
完全接不到它，异常一路冒到 WPF 分发器。**这是全应用唯一一条没有降级路径的解析入口**，
正面违反 AGENTS 第七节"超时、取消、失败降级三件套"。

### 一次改三个解析器

同一形状在三个地方各埋一处：余票（`data.result`）、经停站（`data.data`）、中转（`data.middleList`）。
只补崩的那一处，等于知道这类调用会抛却留下另外两条引信，而余票那条恰恰是亲友最常走的路径。
于是加一个 `JsonShape`（`IsObject` + 安全的 `Prop`），三处统一按"先问外层、取到再问一层"的顺序走。

### 分类不能糊

`ParseFailure` 与 `DataUnavailable` 的分界写进代码注释，因为它决定用户下一步做什么：

- 最外层根本不是对象 → **结构变了**（`ParseFailure`，该换版本）；
- `data` 这一项没给 → 结构变了（`ParseFailure`）；
- `data` 给成一段文字 → **官方这一项没给**（`DataUnavailable`，等一会儿或去官网看）。

把第三条说成"这个版本查不了"，用户就会去要一个并不存在的新版本——这跟把 `NoResult` 说成
"出错了"是同一类错误（AGENTS 七.6）。

### 判据怎么证明它真的会响

第一次植入违例（把 `JsonShape.Prop` 换回 `data.TryGetProperty`）**测试仍然全绿**——
因为我在它前面加的 `IsObject(data)` 守卫先短路了，那条不安全调用根本走不到。
改成把守卫一起拆掉再跑，测试才报出日志里那个原样：
`Expected: QueryException / Actual: System.InvalidOperationException`。
**"植入了违例"和"违例走到了那一步"是两件事**，前者容易做假而不自知。

顺带补了 `StopStationParserTests`（此前**这个解析器一条测试都没有**，六条：站序、首站占位时刻、
外层文字、非对象外层、混进非对象条目、零站）。样本存的是"具名字段数组 + 元信息"，
所以测试里重新包一层 `data.data` 信封再喂——与 `Samples.Response` 对余票样本做的事一样。

测试 276 → **286 全绿，0 警告**。

### 包的事

崩溃修完，rc2 那个 exe 已经带着它了——所以**重出一次包**，构建点跟着换。
旧 zip（`6a2fbc49…`）**从未分发**（名单按用户决定留空），换掉不算 SPEC-006 §六 说的"静默替换"，
但校验和与构建点的变化必须写在说明里，而不是让两个 rc2 各自漂着。

## 十六、改的是规定，不是那一格

用户的话是"名单直接就不填"，接着又要求把条件②本身改掉。这两句的差别值得单独记：

- **只留空**：那张表还在规范里，于是每次出包都欠一项"没做完的"，
  而它其实永远不会被填——一栏长期为空的检查项，比没有这项检查更糟，它教会所有人跳过这一节。
- **改掉规定**：②从此只留"发送时把试用声明那句原话带给对方"，名单不再是要件；
  §一 从四条变三条，§四 清单同步改写，理由写进规范正文。

**为什么同意撤**：那张表从来没被填过，空表提供的诊断价值是零；而它原本要解决的问题
（"是这个包坏了还是这台机器的事"）本来就不靠名单——每条日志都带版本与构建戳，
出问题的机器把日志发回来就够了，"哪一版、什么时候"在文件里不在表里。
**为什么这不算放松风险防线**：① 第一屏试用声明、③ 反馈走日志文件、④ 发过 rc 不等于验收过，
三条一条没减，`v1.0.0` 的清单一个字没松。**放开的是记录，不是声明。**

历史文件不改：`发布/0.4.0-rc1/说明.md`、`0.3.0-rc5/说明.md`、旧开发日志与 TASK-57 的原文
都留着"名单"字样——它们记的是**当时有效的口径**，把历史改成现在合规的样子，
下次就没人知道这条规定是什么时候变的、为什么变。

包不用重出：名单从来只出现在仓库里的说明表，包内两份文本没有它。
