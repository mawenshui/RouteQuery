# 问"下一版本做什么"之前，先把"有没有计划"查实

用户给的分支条件是：有下一版本的计划就继续实现，没有就把需要他明确的问题列出来。
所以这一轮没动代码，做的是**查计划文档到底有没有 V2 的条目**——结论是没有，而且"没有"的方式值得记下来。

## 一、查实结果

- `计划/…实施计划.md` 只有 46 个任务、6 轮，全部是 V1。第九节"明确不在本计划内"逐条列了
  余票监控与通知、读取订单与常旅客、本地中转图、多站组合搜索、行程对比、导出分享、多语言，
  并写明"计划里若出现这些，说明范围蔓延已经发生，应当回到需求文档处理"。
- `需求/…需求文档.md` 第十三节"V2 候选（不进 V1，仅登记）"6 条，**只有登记和前置条件，没有优先级**，
  也没有一条被写成 FR/NFR 那样的可验收条款（功能需求编号止于 FR-36）。设计文档 一~十五 节 + 附录 A
  里没有对应章节。
- 所以按 AGENTS 第四节（需求 → 设计 → 计划 → 实现，未过上游门禁不得开始下游），
  **V2 现在不能"继续实现"，连"实现什么"都还没有条款**。这时候直接写代码就是拿实现当设计用。

## 二、按"要不要动合规"把 6 条候选重新排了一遍

这一步不是给候选排序，而是把"我能自己往下走的"和"必须你拍板的"分开，因为它们的成本根本不在工作量上。

| 候选 | 前置条件里真正卡住的东西 | 谁能定 |
|---|---|---|
| 行程对比（两趟车并排比） | 只依赖 FR-14 数据结构稳定；**不新增任何官方请求** | 我可以先补需求与设计 |
| 多站组合搜索（同城多站一起查） | 请求数成倍增加，要先改 SPEC-007 节流表 | 额度上限要你定 |
| 本地中转图算法（自主拼方案） | "方案由我们算出来"与第七节"数据来源单一性"直接冲突 | 要你定，且要改规范 |
| 起售时间到点提醒 | TASK-43 的验收判据里写着"**应用中不存在任何定时器**" | 做了就等于推翻自己 |
| 读取订单与常旅客 | 把工具从"查询"变成"账号代理"；不做清单②的延伸 | 建议永久不做 |
| 余票监控与通知 | 撞 AGENTS 第四节"禁止高频轮询"，且**风控后果由亲友的账号承担** | 必须你明确同意 |

判断留在这儿，不写进规范：**候选的吸引力排序 ≠ 可以开工的排序**。呼声最高的那条恰好是最贵的一条。

## 三、两条技术债（不是版本功能，但会在下个版本咬人）

- **打包没有脚本**：`publish → zip → 计算 SHA → 写说明` 每版都是手工。已经出过一次事故
  （`7c48ed2` 的提交信息说"可执行件与验收说明"，说明文件其实因为编码问题没写进去）。
- **`OfficialClient` 是具体类**，服务层两条纪律——扩展查询"遇风控整批中止"、中转"会话失效即清除"——
  写不了测试。要么给它加一层接口（会牵动第六节的收敛规则），要么继续靠实跑。上一版选了后者，
  理由留在这里：不为了凑测试先改生产代码。

## 五、改到一半发现：其中一条是我误判的，而且误判了两次

我上一轮把三条用例判成"用例本身有问题"，实际只有一条半是真的。

**第一次误判——TC-D10**：我写的是"两段各自可展开经停……不在 FR-06 的验收标准里"。
这句只对着 FR-06 核对过，而需求 6.4 里有 **FR-15「中转方案分段展开（P1）」**，验收原话就是
"两段各自可展开、可折叠，互不干扰"。**用例没有超范围，缺的是实现**：
`计划/` 里管经停的 TASK-21 判据只写 FR-14，没有任何任务认领 FR-15，`设计/` 也没有这一节。
也就是说这是**计划漏项**，不是范围蔓延。我把"没人认领"读成了"不该存在"——
这个错的性质和上次那条"提交信息说了但没做的事"是一样的：**对外说过的话要回头核对，
但核对时必须把需求全节搜一遍编号，而不是找一个最相近的条款比对了事。**

**第二次误判——TC-A8**：我把它写成"属于新增，不在修 bug 范围内"，问用户要不要做。
实际 FR-04 的校验表逐条写着 `请选择出发车站` / `出发站与到达站不能相同` / `所选日期不在可售范围内`，
还明确要"**输入框标红**"。现在三种非法输入共用一句 `错误_输入无效`，用户读完不知道该动哪个框——
**这是不符合 P0 需求**，我却在问"要不要加功能"。拿"新增范围"当借口不去做本来就该做的东西，
比把漏项当需求更隐蔽，因为它看起来像是在尊重门禁。

**顺带查出的第三个问题**：验收报告的汇总写的是 24/5/17/3=49 条，而用例只有 46 条——
分组口径串了，几条"自动＋实跑"的混合行被重复计入。现在按表格逐行数：**27 有自动化证据
（其中 9 条界面表现仍欠肉眼）/ 7 只有实跑或结构证据 / 12 完全未验证 / 0 用例待改 = 46**。

**可行性核实**（决定 FR-15 能不能补进 V1 的关键）：官方 `lcQuery` 每一段自带 `train_no`、
`from_station_telecode`、`to_station_telecode` 和**该段自己的 `train_date`**（样本里段一 10-11、段二
10-12）。所以调 `API-04` 的四个参数全部由官方给，**不需要我们推日期**——这一条如果不成立，
补做 FR-15 就等于拿推断值当下一句话，那才是真的撞第七节红线。

用户据此定：**FR-15 补进 V1（TASK-47）**，不推到 1.1、也不删用例。

## 七、V2 首批立项（只产文档，一行代码没动）

用户定了 V2 第一条做**行程对比**，并要"先收尾 V1、同时并行补 V2 的需求与设计"。
按 AGENTS 第四节，这正是当下唯一不越门禁的动作：需求 → 设计 → 计划 → 实现，
补上游文档不算提前开工，改代码才算。

**选择标准写进了需求文档本身**，因为"哪个最有用"和"哪条能开工"是两回事：
六条候选里只有行程对比的全部输入都已经在屏幕上——其余五条的前置条件分别指向
SPEC-007 频率表（余票监控、多站组合、到点提醒）、第七节数据来源单一性（本地中转图）、
以及个人数据合规（读取订单）。动它们要先改规范，改规范不是"顺手"的事。

顺手把第十三节里两条候选**没说清的冲突**补上：

- 本地中转图算法：由我们自己拼出来的换乘方案**不是官方给的方案**，与第七节正面相撞。
  以前只写"需要稳定的线路-车站关系数据"，那说的是工程量，没说合规冲突。
- 起售时间到点提醒：TASK-43 的验收判据里明写了"应用中不存在任何定时器"，
  而那条判据**已经验收过**。做提醒等于推翻自己已验收的东西，必须按需求变更走。

FR-37 的条款里有一条别处没有的硬约束：**同批次同 OD 才可比**。理由不是审美——
同一趟车隔一天余票和起售时间就变了，如果按车次号跨批次保留勾选，
就等于把昨天看到的数摆进今天的比较表，那是 NFR-18 明令禁止的"用缓存冒充当前值"，
而且它看起来完全正常。设计附录 B.3 为这一条单独开了一节，并给了"批次令牌"这个实现形态。

计划侧新增 §十二（TASK-48 ~ 51）**标注"尚未开工"**，前置条件第一条是"V1 已打出 `v1.0.0`"。
把这句话写死，是因为并行开 V2 文档这件事本身就有变成第二次范围蔓延的风险。

## 九、出了 0.3.0-rc4 的包（本地，不挂 Release）

用户选了"打包我再人工验证"这条路。原因很直接：**GitHub 上那个 rc3 的 exe 里没有本轮两处改动**
（构建点 `024f824`，本轮是 `9ea64e6` 之后），拿旧包验新行为只会得到"我改了个寂寞"的结论。

出包过程里撞见一个真实的缺陷，而且是我的缺陷：

- 包里的 `变更日志.txt` **停在 rc2**，正文里还带着 `FR-33`、`哨兵值`、"Parse 在闸门委托外"这类
  内部说法。而这个文件自己的写作规则第一条就写着"面向使用者，不出现类名与内部编号"。
  更难看的是 rc3 那版**根本没进这份 txt**。
- 根因不是"忘了写"，是**这份文件是手工维护的副本**。凡是"从 A 手抄一份 B 出去"的形态，
  迟早会漂。所以本轮把 `使用说明.txt` / `变更日志.txt` 改成**由仓库里的文档生成**，
  并把生成规则写进脚本：markdown 的 `#`、`**`、行内代码标记去掉，表格转成"a —— b"一行一条。
- 顺手发现两处小事实需要更正记录：zip 内中文文件名的编码方式变了（rc3 那份是本机代码页、
  没有 UTF-8 标记，第三方解压工具会显示乱码；rc4 有标记）；`<Version>` 一改，
  关于页、日志头、包名三处跟着一起变，这是"版本号唯一来源"这条规矩的回酬。

**没挂 GitHub Release**：SPEC-006 第四节的清单里还有 4 项必须由人做，验收报告统计的
18 项需要有人参与的用例一条都没跑。把 rc4 挂出去就等于对外说"可以用了"，而这句话现在不成立。

**遗留**：`publish → 转文本 → 压包 → 算校验和 → 写说明` 这条链子只做了一半的脚本化，
`<Version>` 仍是手改。下一版（V2）第一件事我建议就是把它做成一条命令——
理由不是省事，而是这次证明了一件事：**手工维护的副本一定会漂，而漂了没人报警。**

## 十、重打了一次包，因为第一次的构建戳对不上

第一遍是**先 publish 再提交版本号**：exe 里嵌的源码戳落在上一个提交 `9ea64e6`，
而它的源码树其实带着未提交的 `<Version>` 改动。这样"这个 exe 对应哪次提交"就没法核对——
而 rc3 那次我刚把这句话写进文档（"tag 落在 `024f824`，也就是包里那个 exe 的构建点"）。
自己刚承诺过的可核对性，下一版就做不到，这比 bug 更糟。

所以顺序改成：**提交版本号与发布文档 → 从干净树 publish → 压包 → 算校验和 → 回填说明**。
现在 exe 内嵌戳 = `5a490af` = 构建点，校验和也全部重算并回填。

**冒烟测试**：把包里的 exe 单独拷到空目录启动，进程正常起来并稳定 55 秒后手动结束，
临时目录已清。这只能证明"单文件包不是空壳、能启动"，**不能证明任何界面行为**——
本轮两处改动要看的效果（中转两段展开、输入框标红）仍在你要点的清单上。
