## 一、排期原则

1. **先让不确定性归零，再写功能代码。** 第 0 轮全是补核实任务，不做任何界面与业务功能——因为设计里还有 4 项残余未知（候补态、席别码全集、无结果/风控样本、官方 URL 形态），它们各自的结论都会改变代码写法。先写后补必然返工。
2. **按"能否独立验证"切任务。** 每个 TASK 的完成判据都必须能被第三人单独判定（一条测试、一次截图、一条 grep 结果），不接受"写完即完成"。
3. **解析层排在网络层之前。** 样本已在仓库里，解析器可以完全离线开发并测透；把它排在前面，等真接口通时它已经不是风险项。
4. **区间扩展排在直达链路打通之后。** 它依赖经停站与余票列，而这两者的可用性要在直达链路上先验证一次。
5. 规模标记：**小** ≈ 一次会话内可完成；**中** ≈ 需要设计+实现+测试完整循环；**大** ≈ 应再拆分。

## 八、里程碑与阻塞关系

```
第0轮 补核实（TASK-00~05）
   └─▶ 第1轮 骨架与离线解析（06~13）      ← TASK-11 是关键路径
          └─▶ 第2轮 网络与直达打通（14~20）  ← 第一个可自用里程碑
                 ├─▶ 第3轮 钻取/筛选/扩展（21~28） ← TASK-25 与 11 并列高风险
                 └─▶ 第4轮 登录/中转/本地数据（29~35）
                        └─▶ 第5轮 验收与发布（36~42）
```

### 第 2、3 轮实跑发现的四处问题（都不是编译能抓到的）

1. **一次成功的查询永远停在转圈上。** `ApplyLocalView()` 对"还在加载中"是直接 return 的，而 `QueryAsync` 数据到手后先调它、之后才把状态从 `Loading` 落走——顺序反了，界面就再也没往下走。69 个单元测试全绿、编译零警告，**只有真点一次才暴露**。结论：界面层需要一条"查询成功 → 状态是 Results 且行数 > 0"的可自动执行断言，而现有测试工程是 `net8.0`、App 工程是 `net8.0-windows`，引用不上，得另立一个 windows 测试工程（见第十一节）。
2. **选完出发站、在到达站打字，出发站的候选弹层会自己弹回来。** 两个输入框共用一个"刷新候选"方法，把对面那份列表也填上了，而弹层的开合绑的是候选数量。改成每个输入框只刷新自己的候选，并在点查询时主动收起。
3. **`Unknown20` 被打到了屏幕上。** 列 20 / 27 / 33 的中文名官方从未给出，代码用 `seat.ToString()` 兜底，于是亲友看到英文枚举名——违反"错误提示必须是人话"。改为统一显示"未确认席别"，余票状态照常给出。**这是"不猜标签"的代价，记为已知问题 K-03 而不是 bug。**
4. **保存"最多扩展站数"会顺手抹掉别的设置。** 原写法是 `Save(new AppSettings(clamped))` 整体覆盖；把首次声明确认标记（FR-20）放进同一个文件后，用户改一次站数就会把"已看过声明"清回 false，下次启动再弹一遍。改为在现有值上只改这一项。
