## 一、设计的三条主导思想

这份架构不是按"通常怎么写 WPF 应用"来组织的，而是被三个现实条件逼出来的形态：

1. **外部接口是唯一不可控源，且失效方式包括"静默给错数据"。** 所以架构的核心不是 MVC 分层，而是**把不确定性关进一个可整体替换的盒子**，并让失效**必然**以显式错误暴露，绝不让错位数据流到用户眼前（NFR-16）。
2. **应用会持有亲友本人的账号会话。** 这是 v2.0 引入的最重责任。所以凭据与会话的路径**必须在结构上无法扩展**成"替用户操作账号"——不是靠约定，而是靠"没有任何接口可以传密码进来、没有任何类型能承载订单数据"。
3. **使用者是不看文档的亲友。** 所以错误处理不是日志问题而是产品问题：每一种失败都必须预先对应一句人话和一个下一步动作（BF-02 的 6 行 → 6 条文案）。

## 二、关键设计决策

| 编号 | 决策 | 备选 | 为什么选它 |
|---|---|---|---|
| DEC-01 | 四程序集分层，依赖方向 `App → Core ← Data`，`Core` 不依赖 UI 也不依赖网络 | 单程序集 + 文件夹分区 | 单程序集写起来省事，但"App 不许出现 URL"就无法用编译器保证，只能靠人盯。分层让红线变成**编译不过的错误** |
| DEC-02 | 解析采用**版本化列布局描述表 + 三项结构自检 + 自检不过即停** | ① 猜 mapper（已证明不存在）；② 直接硬编码下标散在各处；③ 尽量解析、失败字段留空 | 实测响应无 `mapper`，下标不可避免。真正能选的只有"下标放几处"和"错了怎么办"。方案 ③ 会让 `G531` 的票价错挂到 `G102` 上并照常显示，那是这个应用最坏的结果 |
| DEC-03 | 会话通过**端口/适配器**获取：`Core` 定义 `IOfficialSessionProvider`，`App`（WebView2）实现，`Data`（HTTP）消费 | 在 Data 层直接持有 WebView2 控件 | WebView2 是 UI 组件，放进 Data 会让数据层依赖 UI，违反 DEC-01。端口反转后运行时能拿到会话，编译期依赖方向不变 |
| DEC-04 | 请求节流做成**单点闸门** `RequestGate`（并发 1、最小间隔、单动作预算 ≤3、日计数），所有官方调用必须经它 | 各处 `await Task.Delay(3000)` | 散点延时会被"再加一个功能"逐个绕过。集中闸门使 SPEC-007 第四节那张表可以用一个类型审计，也让"登录态阈值收紧一半"只改一处 |
| DEC-05 | 直达与中转在编排层**独立聚合**，各自成败互不影响 | 一次 async 里顺序做完 | FR-06 要求"中转失败不得影响直达"。顺序写法里一处抛错整链失败，且很难看出为什么 |
| DEC-06 | 接口路径后缀按 302 `Location` **运行时发现 + 本地缓存**，缓存失效时重新发现一次 | 把 `queryG` 写死 | 实测 `query` → 302 → `queryG`，后缀历史上多次变化。写死等于把 RISK-02 变成必然发生 |
| DEC-07 | 站点匹配建**内存多路索引**（站名/前缀/包含/全拼/首字母），并按码表的**城市代码**分组同城站 | 每次查询线性扫 3404 条 | 线性扫 3404 条其实只要零点几毫秒，但无法实现"前缀优先 + 同城聚合"的排序质量。索引一次构建，进程内复用 |
| DEC-08 | 未登录时中转区是**引导态**（正常视觉、可选动作），不是错误态（红色、感叹号） | 直接弹"需要登录" | RISK-20：不登录是合法使用方式。用错误态会让亲友以为工具坏了 |
| DEC-09 | 本地持久化用 **JSON 文件 + 临时文件写完再原子替换**，不引 ORM、不用 SQLite | SQLite | 数据量是"20 条收藏 + 30 条历史"这个量级，SQLite 带来的体积、初始化、损坏恢复成本远大于收益。原子替换专治 FR-18 的"更新中断导致码表损坏" |
| DEC-10 | WebView2 浮层由应用**渲染当前域名文本**，并做**域名白名单阻断**（仅 `*.12306.cn`） | 完全裸展 WebView2 | 见本节下方的诚实说明 |
| **DEC-15** | 检查更新走**独立的 `HttpClient` 实例**，不经过 `RequestGate`，且与官方客户端不共享 CookieContainer | 复用主客户端省事 | 共享会把官方站点的会话 Cookie 带到 GitHub 请求上（或反之），这是凭据泄漏的真实路径；而共享闸门会让"取一个版本号"占掉官方请求预算、并把节流语义搅浑。**隔离之后两者各自可审计**：日志里官方请求数与更新检查数互不污染，SPEC-005 TC-U17 与 SPEC-007 §6 的抓包判据才成立 |
| **DEC-11** | 请求闸门按**动作类型分级预算**：`Basic` ≤3 次、`Extension` ≤10 次（硬上限 12），二者共用同一串行队列与 ≥3 秒间隔 | 沿用统一 ≤3 次；或为扩展单独开一条不限流的通道 | 统一上限会让功能不可实现，另开通道等于绕过红线。分级后每一级各自可审计，且**串行与间隔不因分级而放松**——放大的只有次数，不是节奏 |
| **DEC-12** | 扩展的触发主信号是 **`canWebBuy`（列 11）为 `N`**；余票列（20–33）用于细化展示 | 只用余票列判定；或用 `canWebBuy` 但把候补也算作有票 | `canWebBuy` 是官方口径的"可否网上购票"，语义清晰、跨车型已验证。**v1.3 补充**：余票列语义已确认（Q-10 关闭），故可用于展示与筛选，但**候补（列 37 + 席别值（判定式见 SPEC-007 v1.7 规则 5））不得算作有票**——那会让扩展入口出现在其实买得到票的车次上，或反过来把能候补的车当"没救" |
| **DEC-13** | 候选 = **该次车经停站序上的连续区间扩展**（前移 p 站 / 后延 q 站 / 两端且 p+q ≤ K），按 `p+q` 升序生成后**截断到预算** | 枚举同城所有车站；或按里程等距取样 | 经停站序是唯一确定"这趟车在哪些站能上车"的事实来源，且天然是有限集合。同城枚举会产生无法上车的候选（该车不停这些站），属于纯浪费请求 |
| **DEC-14** | Δ 金额**必须同席别对齐**，任一侧价格缺失即显示"无法计算"，**禁止**显示 0、负数或估算 | 缺失时按 0 计；或用相邻席别价格替代 | Δ 直接决定用户愿不愿意多付钱。把"缺失"算成 0，等于告诉用户"不用多花钱"，那是本应用可能造成真实金钱损失的唯一路径 |
| **DEC-16** | 列 20 / 27 / 33 这三个**官方从未给出中文名**的席别列，界面统一显示"未确认席别"，余票状态与票价照常按官方值显示 | 直接不显示这三列；或把内部枚举名 `Unknown20` 打出来；或按位置猜一个中文名 | 猜标签违反 NFR-18；打枚举名违反 AGENTS 七.3"人话"；不显示则是藏掉官方给了的数据。显示"未确认席别"是三者里唯一既诚实又可读的口径——**它把"我们不知道"这件事本身告诉用户，而不是让他以为知道了** |
| **DEC-17** | 候选站点的**提交只有一条路径**：列表选中项 → ViewModel 属性。代码后置只负责把 ↑↓ 转成"选中哪一条"；每个输入框只刷新自己那份候选；点查询时主动收起弹层 | 鼠标走 `MouseUp` 事件提交、键盘走另一套提交 | 两条提交路径必然出现"看着选中了，点查询却说没选站"。实测正是如此：在到达站打字会把出发站的候选重新填上，弹层自己弹回来 |

### DEC-11 ~ DEC-14 的完整设计见附录 A（区间扩展）。

### DEC-10 的已知局限（写下来而不是藏起来）

自建浮层里显示一个"当前地址"文本，**信任度低于真实浏览器的地址栏**——用户可以选择相信的程度有限。缓解与代价都摆明：

- 缓解：① 白名单阻断，非 `*.12306.cn` 一律停止导航并红字警告，不允许在应用内继续；② 域名文本从 `CoreWebView2.Source` 直接读取，不由我们拼接；③ 浮层常驻标注"你正在 12306 官方页面登录，本工具不接收密码"。
- 仍不能防的：如果用户本就想在伪造页面输入，应用无法像浏览器那样依赖用户核对 UI 细节。
- 结论：因此 **FR-24 的登录必须是完全可选的**。不登录 = 完全不接触这个风险面。设计上把"登录"做成一次明确点击，绝不默认弹出。

## 四、核心数据模型

```csharp
/// <summary>车站。城市代码与城市名来自码表第 7、8 字段，用于同城聚合（FR-01）。</summary>
public sealed record Station(string Name, string Telecode, string Pinyin,
                             string ShortPinyin, string CityCode, string CityName);

/// <summary>一趟车在某个查询区间上的事实。对应 FR-08 直达车次。</summary>
public sealed record TrainJourney(
    string TrainCode,           // G531
    string TrainNo,             // 240000G53106，经停钻取用的透传标识
    Station From, Station To,
    Station StartStation, Station EndStation,   // 始发终到，用于展示"本次查询区间只是全程一部分"
    TimeOnly Departure, TimeOnly Arrival,
    TimeSpan Duration,
    bool ArrivesNextDay,        // 显式建模跨零点，禁止界面推断（SPEC-004 六.5）
    bool CanBookOnline,
    IReadOnlyList<SeatAvailability> Seats,
    DateTimeOffset? ReleaseAt   // 第 55 列放票时间
);

/// <summary>席别余票。Raw 字段原样保留官方口径（FR-13 / RISK-13）。</summary>
public sealed record SeatAvailability(SeatClass Class, string RawRemaining, decimal? Price);

/// <summary>换乘方案。IsTransferSameStation 与 AvailabilityKnown 必须显式建模。</summary>
public sealed record TransferPlan(
    TrainJourney FirstLeg, TrainJourney SecondLeg,
    Station TransferStation, bool IsSameStation,
    TimeSpan TransferWait, TimeSpan TotalDuration,
    bool AvailabilityKnown      // Q-01 未定的落点：界面据此决定是否显示"余票需点入查看"
);
```

`TransferPlan.AvailabilityKnown` 这个布尔存在的唯一理由：Q-01（中转接口是否给全两段余票）要到有登录会话后才能确认，而界面文案已经需要先定下来。把它建模成数据字段，界面就不必在两种口径下各写一套判断——等核实完成，只改解析层对该字段的赋值。

## 五、解析层（本应用的技术核心）

### 5.1 处理流水线

```
HTTP 响应文本
  ↓ ① 顶层形态判定：能 JSON.parse？
  │     否 → 内容是 HTML 且含 passport → UpstreamRejected(需登录)
  │     否 → 其他 HTML/异常页        → UpstreamRejected(疑似风控)
  ↓ ② status==true && httpstatus==200 ？ 否 → 按 messages 判 NoResult / UpstreamRejected
  ↓ ③ 列数 == 布局表声明的列数 ？        否 → ParseFailure  ★不出数
  ↓ ④ 逐条结构自检（车次号 / 时刻格式）  不过 → ParseFailure ★整批不出数
  ↓ ⑤ 按布局表取列 → TrainJourney
  ↓ ⑥ 席别/票价解码（PriceDecoder + SeatCodeMap）
  ↓ ⑦ 用 data.map 回填站名（三字码 → 中文）
  → 强类型结果
```

第 ③④ 步是 NFR-16 的实现点：**"整批不出数"而不是"这条跳过"**。理由是列错位会污染全部字段，逐条容错的产物是一堆看起来很正常的错误数据，那比空列表危险得多。

### 5.2 布局描述表（v1.3：列语义已全部由官方脚本确定）

```csharp
/// <summary>
/// API-02 结果的列布局。全库唯一允许出现列下标的位置（SPEC-004 一、硬约束 1）。
/// 列名与语义取自官方渲染脚本 queryLeftTicket_end_js.js 的字段赋值代码，
/// 并与页面 DOM 同瞬间逐格验证；来源标记与核实日期必须一并记录。
/// </summary>
public static class LeftTicketColumnLayout
{
    public const int LayoutVersion = 2;
    public const int ExpectedColumnCount = 58;              // 跨 C/D/G/K/T/Z 124 条样本验证
    const string Src = "Confirmed-ByOfficialScript@2026-10-09";

    public static readonly ColumnSpec TrainCode   = new(3,  pattern: @"^[GDCZTKLY]\d{1,4}$", Src);
    public static readonly ColumnSpec TrainNo     = new(2,  Src);
    public static readonly ColumnSpec Departure   = new(8,  pattern: @"^\d{2}:\d{2}$", Src);
    public static readonly ColumnSpec Arrival     = new(9,  pattern: @"^\d{2}:\d{2}$", Src);
    public static readonly ColumnSpec Duration    = new(10, pattern: @"^\d{2}:\d{2}$", Src);
    public static readonly ColumnSpec CanWebBuy   = new(11, pattern: @"^[YN]$", Src);
```

设计上的三点考虑：

1. **`Unverified` 标记保留为机制，但当前只剩 3 列在用**。`gg_num`/`yb_num`/`srrb_num` 的中文标签官方页面没有独立列，标签为 `null` → 只透传、不显示、不参与筛选。机制留着是因为列布局还会漂移，将来新增或改位的列仍要先进这个状态。
2. **`Availability` 用官方字段名而不是下标做键**，于是"某席别对应哪一列"这件事在代码里是可读的；审阅者对照 SPEC-007 的表就能验证，不需要读解析代码。
3. **来源标记是硬要求**（`Confirmed-ByOfficialScript` / `Confirmed-ByObservation` / `Unverified`）。这一版之所以能定论，是因为找到了官方自己的赋值代码；此前两次靠取值推测都留下了错误结论（v1.1 的 mapper、v1.2 的"列 34 可能是余票"）。**标记的存在就是为了让下一个人在半年后知道某个结论值不值得信**。

自检规则与下标同处一表，因此审阅者只需看一个文件就能回答"接口变了要改哪里"。

### 5.3 票价与席别

- 价格串按 **每 10 字符一条记录** 切分：`席别码(1) + 以分为单位的价格(6) + 附加标记(3)`。**该规则已跨车型确认**（高铁 G/D/C 与普速 K/T/Z 同一套）。

  | 原始 10 字符 | 解析 |
  |---|---|
  | `9017400003` | 席别 9，`017400` 分 = **174.00** 元，标记 003 |
  | `O004900021` | 席别 O，`004900` 分 = **49.00** 元，标记 021 |
  | `1002150021` | 席别 1，`002150` 分 = **21.50** 元，标记 021 |
  | `4010250002` | 席别 4，`010250` 分 = **102.50** 元，标记 002 |

  这三条同时是 `PriceDecoder` 的固定测试向量（第十二节）。
- **同一席别出现多条记录时取第一条**，不做平均、不做猜测（Q-05 未定；`O=49.00` 与 `O=49.03` 并存、`1=21.50` 与 `1=21.53` 并存均已实测到）。
- 席别码实测集合：高铁 `9 M O D W J I`，普速 `1 3 4 6`。中文名集中在 `SeatCodeMap`；**未登记代码原样透传并写日志，绝不抛异常**。
- **余票已接通（v1.3，Q-10 关闭）**。v1.2 那张"核实前如何降级"的表作废，现行规则如下：

  | 位置 | 现行做法 |
  |---|---|
  | FR-09 席别余票简摘 | 显示官方原始值：数字原样、`有`、`无`、空 → `—`；由列 37 + 席别值（判定式见 SPEC-007 v1.7 规则 5） 判定为候补时显示 **"候补"** |
  | FR-11 余票筛选 | 正常上线。**三态**：`有票` = 数字或 `有`；`无票` = `无`/空；`可候补` = 无票但候补标记允许。**候补不算有票** |
  | FR-13 席别明细 | 余票取官方列名表、票价取席别码表，**两套编码不得混用**，分别映射后再关联 |
  | 任一数据取不到 | **报错**（新增错误类型 `DataUnavailable`）。禁止用 `—`/`0`/`无票` 顶替，禁止用码表或常识推断（NFR-18、SPEC-007 规则 6） |

- 无座票价与同席别座席价相同（官方 `WZ` 与 `O`/`1` 实测同值），界面显示该价而非空值。
- **本项目不调用 `API-06 queryTicketPrice`**：实测其结果与列 39 逐项一致，而它在 curl 直连下被 302、只在真实页面上下文可用。依赖它等于依赖"复刻浏览器流程"，与请求头最小必要原则冲突，且会让"多买几站"每候选请求数翻倍而使预算不成立（附录 A.5）。

## 六、会话与登录设计

### 6.1 边界

```
用户在中转页签点"登录"
   ↓
App.Web.OfficialLoginPageHost   ← WebView2 唯一用途就是这一屏
   ↓ 用户自己在官方页面输入账号密码与验证码
   ↓ 官方判定登录成功
App.Web  →  IOfficialSessionProvider.TryCaptureSession()   （Core 端口）
   ↓ 实现读 CoreWebView2.CookieManager.GetCookiesAsync("https://kyfw.12306.cn")
   ↓
Data.ProtectedSessionStore  →  DPAPI(CurrentUser) 加密 → session.protected
   ↓
Data.SessionCookieInjectHandler  在后续官方请求上附带
   ↓
TransferQueryService 调 lcQuery（经 RequestGate，1 次）
```

结构上的三道"防越界"设计：

1. **没有任何类型能承载密码**：`IOfficialSessionProvider` 只有 `TryCaptureSession()` / `Clear()` / `HasValidSession` 三个成员，不存在 `Login(user, pwd)` 这类方法可写。
2. **`Data` 拿不到 Cookie 明文集合**：端口返回的是"会话是否有效"与一个内部注入句柄，Cookie 值不穿过 `Data` 的公开签名。
3. **交易类能力没有入口**：`RequestGate` 只注册了 `API-01 ~ API-05` 五个端点。要下单，必须先在这个类型里加端点——那是一个显眼的、评审必然看到的改动。

### 6.2 会话状态机

```
未登录 ──用户成功登录──▶ 已持有 ──请求返回 302 passport──▶ 已失效
  ▲                        │                                 │
  └──────清除/过期─────────┴──────────清本地 + 回引导态───────┘
```

- **已失效** 状态下**必须**立即清掉本地会话再提示，不得保留一个已知无效的会话反复撞（那既是风控风险，也是 RISK-03 的账号风险）。
- 启动时若存在会话，**不做任何网络校验**（避免一打开应用就自动请求官方），只在首次需要它时按结果判定有效性。

### 6.3 DomainGuard

`NavigationStarting` 时检查目标域名，非 `*.12306.cn` → 取消导航 → 显示红字"已阻止跳转到非官方站点"并保留"用系统浏览器打开"选项。`NewWindowRequested` 一律取消，不允许 WebView 自己开新窗口绕过宿主。

## 七、请求管线与节流

`RequestGate` 是唯一出口，落实 SPEC-007 第四节数值表：

| 检查（按序） | 不通过时的行为 |
|---|---|
| ① 当前是否有在途请求（并发 1） | 直接拒绝，文案"上一次查询还在进行" |
| ② 距上次请求是否 ≥ 3 秒 | 拒绝，文案"稍等几秒再查询"（**不排队**，避免用户连点后积压一串请求依次打出去） |
| ③ 本用户动作预算是否 ≤ 3 | 拒绝第 4 个请求，中转降级 |
| ④ 当日计数是否超阈值（游客 200 / 登录 100） | 拒绝并提示降低频率 |
| ⑤ 通过后：记序号 → 发请求 → 记数 | 序号用于丢弃迟到响应（FR-08） |

超时统一 15 秒（NFR-01 硬性上限）；`CancellationToken` 由 `LinkedTokenSource(用户取消, 超时)` 合成，符合 SPEC-004 四节的"三件套"。

编排层 `QueryOrchestrator`：

```csharp
var direct  = SafeAsync(() => trainQuery.SearchAsync(criteria, ct));
var trans   = SafeAsync(() => transferQuery.SearchAsync(criteria, ct));
await Task.WhenAll(direct, trans);   // 二者互不牵连，DEC-05
// 注：并发 1 的限制由 RequestGate 内部串行化，Task.WhenAll 只是发起，不会造成并发打击
```

这里有个**必须写进代码注释**的微妙点：看起来是并行，实际由闸门串行化。不写清楚，后来人很容易把闸门当成 bug"顺手修掉"，从而真的开始并发打官方接口。

## 八、站点匹配与码表

- 加载：内置 `stations.json`（由 `station_name.js` 一次性转换，UTF-8，3404 条）。
- 索引：`站名→条目`、`前缀 trie`、`全拼→`、`首字母→`；同城按 `CityCode` 聚合。
- 打分：精确全名 100 > 前缀 70 > 首字母 50 > 包含 30；同城内按站名长度升序（短名通常是主站，如"北京"优先于"北京南"）。
- 候选面板**永远显示站名全称 + 城市名**，不允许出现同名歧义的简写（FR-01 边界）。
- 更新：仅手动触发（`StationUpdater`）→ 下载临时文件 → 校验"条目数 ≥ 内置版本 90% 且每行 10 字段" → 原子替换。任一步失败保留旧文件并提示（FR-18 验收②）。**不做启动自动更新**。
- 弱提示：`stations.json` 的 `sourceDate` 超 90 天时，在设置页显示一行小字，不打扰主流程。

六态分离渲染（FR-10，由 `IQueryViewState` 决定，绝不允许"无结果"复用"出错"模板）：

| 状态 | 视觉 | 可做的动作 |
|---|---|---|
| 加载 | 骨架行 + 取消 | 取消 |
| 有结果 | 列表 | 筛选/排序/展开 |
| 无结果 | 中性灰空插画 + "该日期无直达车次" | 换日期、看中转 |

| 错误 | 按 `QueryErrorKind` 分类着色 | 重试（仅 `NetworkUnavailable`/超时） |
| **批量进行中**（v1.2 新增） | 进度条 + `已完成/总数` + 剩余额度 + 停止按钮，**已获候选逐条即时插入** | 停止（保留已获结果）、跳官方 |

`批量进行中` 必须与 `加载` 分开：`加载` 是一次未知时长的等待，用户只能取消；`批量进行中` 是一段**可预估、可分批、可中途叫停且不损失已有结果**的过程。把它画成骨架屏，用户就不知道自己还要等多久、也不知道停下来能保住什么——那是 NFR-17 在界面上的落点。

## 十、错误分类到文案的映射

| `QueryErrorKind` | 触发条件（实测口径） | 界面文案 | 重试 | 对应需求 |
|---|---|---|---|---|
| `InputInvalid` | 本地校验未过 | 定位到具体输入框的一句话 | — | FR-04 |
| `NetworkUnavailable` | DNS/连接/TLS 失败 | "连不上网络，检查一下这台机器的网络再试" | ✅ 1 次 | BF-02 |
| `Timeout` | 超 15 秒 | "官方响应慢，这次查询先取消了" | ✅ 1 次 | BF-02 |
| `UpstreamRejected` | 非 JSON / 异常页 / 302 到非 `passport` | "官方查询暂时不可用，过几分钟再试（不是你的网络问题）" | ❌ | RISK-08 |
| `SessionRequired` | 302 到 `/otn/passport` | 引导态文案，见第九节 | ❌ | FR-06 降级① |
| `ParseFailure` | 列数或格式自检不过 | "官方数据格式有变化，这个版本查不了，请找我要新版" + 写日志 | ❌ | RISK-01 |
| `NoResult` | `result` 为空数组 | 空态，不算错误 | — | FR-10 |
| **`DataUnavailable`**（v1.3 新增） | 官方接口可达但未返回该项数据：经停站数组为空、某席别价格缺失、`API-04` 失败、`API-03` 结构不完整 | 明确说"官方未提供该项数据"，界面对应位置显示**错误提示而不是空白或 `—`**，依赖它的功能入口置灰 | ❌ | **NFR-18**、FR-14、FR-26 |

`DataUnavailable` 与 `NoResult` 必须分开：后者是"官方告诉你这趟没车"，是有效信息；前者是"官方没给这个数据"，**不得被渲染成后者**。同理它和 `ParseFailure` 也不同——`ParseFailure` 是结构变了（需升级），`DataUnavailable` 是结构正常但字段为空（可重试、可告知用户）。把三者混成一个"查询失败"，用户就无从判断该等、该重试还是该换新版本。

`ParseFailure` 文案里"请找我要新版"是刻意的：分发对象是亲友，让他们知道这是**外部变化**而不是他们做错了事，同时也给出唯一有效路径。

## 附录 A、区间扩展（"多买几站"）设计

> 承接需求 FR-26 ~ FR-31 与决策 DEC-11 ~ DEC-14。这是本项目第一个"一个用户动作 → 多次官方请求"的功能，也是第一个会算出**金额**并展示的功能，因此它的每一段逻辑都直接连着钱和风控。

### A.1 术语与问题定义

目标区间 `[i, j]` 指该车次经停站序 `S[0..n-1]` 上用户真正想坐的站序区间。**扩展区间**是任意满足 `a ≤ i` 且 `b ≥ j` 且 `(a,b) ≠ (i,j)` 的 `[a, b]`。定义"多买站数" `extra = (i - a) + (b - j)`。

关键前提：**"站"是站序位次，不是里程**。同一个 `extra = 2`，在城际短途上可能多花 8 元，在干线长途上可能多花 400 元。因此站数本身不构成决策依据，**必须与金额同时呈现**——这也是 FR-28 把两者绑在一行显示的原因。

### A.2 模块归属

| 模块 | 层 | 职责 | 对应需求 |
|---|---|---|---|
| `Core.Logic.ExtensionCandidateGenerator` | Core | 由站序与 K 生成候选，纯函数、不触网 | FR-26 |
| `Core.Logic.ExtensionSorter` | Core | 候选优先级（`extra` 升序 → 距离目标区间近者优先） | FR-26 |
| `Core.Logic.PriceDeltaCalculator` | Core | 同席别对齐、Δ 计算、缺失与负值处置 | FR-28 |
| `Core.Ports.IExtensionQueryService` | Core | 端口定义 | FR-27 |
| `Data.Services.ExtensionQueryService` | Data | 批次执行、按 `train_no` 匹配、预算与中断 | FR-27 |
| `Data.Http.RequestGate`（**改**） | Data | 新增动作类型分级 | DEC-11 |
| `App.ExtensionPanelViewModel` + `Views/ExtensionPanel` | App | 就地面板、进度、停止、金额显示 | FR-27/28/31 |

### A.3 候选生成（纯函数，可完全离线测试）

```
输入: stops[0..n-1]（该车次全程经停站序）, i, j, K∈[1,10]
1. 校验 0 ≤ i < j ≤ n-1，否则返回 InputInvalid（FR-04 前置，绝不触网）
2. 单端前移: p = 1..min(K, i)            → 候选 (i-p, j)
   单端后延: q = 1..min(K, n-1-j)        → 候选 (i, j+q)
   双端:     p=1..min(K,i), q=1..min(K-p, n-1-j)  → 候选 (i-p, j+q)   // p+q ≤ K
3. 去重（(a,b) 唯一）、丢弃不真包含 [i,j] 的项
4. 排序: extra 升序 → (j-b) 与 (a-i) 中较小者优先 → 始发站侧优先
5. 截断: take(min(预算, 候选数))，未取出的个数返回给界面显示"还有 M 个候选未查询"
```

**边界必须有测试**：`i == 0`（目标站即始发站）→ 前移候选为 0；`j == n-1`（终到站）→ 后延候选为 0；两者同时成立（全程票）→ 候选集为空，界面显示"这趟车已是全程票，无法再向前/向后扩展"，**不发起任何请求**。K 越大不代表越好：`K=10` 时候选可达 65 个（`10+10+45`），而预算只有 12，所以截断是常态而非异常。

### A.4 批次执行

```
ExtensionQueryService.RunAsync(journey, K, ct):
  stops  = await stopService.GetStopsAsync(journey.TrainNo)   // 1 次，会话内缓存（FR-14）
  cand   = generator.Generate(stops, i, j, K)
  taken  = ExtensionSorter.Truncate(cand, Budget)             // ≤10，硬上限 12
  foreach c in taken:
      if ct.IsCancellationRequested: yield 已完成部分; break   // FR-27 可中断
      r = await gate.Run(ActionKind.Extension, () =>          // 串行 + ≥3s 间隔
              queryOne(c.From, c.To, journey.TrainNo))
      switch r:
        UpstreamRejected / ParseFailure → **整批中止**，保留已获结果，给出风控/升级文案
        NoMatch(该 train_no 不在此区间)  → 记为"此区间不可售"候选，不猜别的车次
        ok                              → 交 PriceDeltaCalculator 算 Δ，增量推给界面
```

三条不可省略的实现纪律：

1. **增量推送**（`IProgress<T>`）：每完成一个候选就上一条结果，而不是等全批结束。这让"中途停止"有价值，也让 30 秒的等待有反馈（NFR-01 ②类）。
2. **闸门是唯一出口**：批次里不许出现绕过 `RequestGate` 的 `HttpClient` 调用。这一条可用 grep 审计。
3. **中止不等于失败**：整批中止后已获得的候选结果**必须**照常展示，否则用户白等。

### A.5 Δ 计算

```
Δ = 候选区间[席别 s] 票价 − 目标区间[席别 s] 票价
```

- 目标区间与候选区间的票价都来自 **`API-02` 列 39 解码**，**不额外请求 `API-06`**（省一次请求，且两侧同源可比）。该取舍已由实测背书：列 39 解码与官方 `queryTicketPrice` 返回逐项一致（G6701 174.00/79.00/49.00；K599 21.50/102.50/67.50），见 `测试/接口样本/queryTicketPrice-票价样本.json`。**这一条是 FR-27"每候选 1 次请求"预算成立的前提**。
- 席别对齐：两侧席别码集合取交集展示；交集为空的席别显示"该席别在此区间不售"。
- 任一价格为 `null` → Δ 为 `Unavailable`，界面 `无法计算`。
- `Δ < 0` → **视为解析异常**：写日志、显示"价格数据异常"、该候选降级为只显示票价不显示差额。理论上更长区间票价不应低于短区间，出现负值几乎必然是列位或席别对齐错了，不能当正常数据渲染给用户。
- 界面常驻："票价为票面区间价格，多出的区间属于自愿弃用、不退款；实际以下单时官方显示为准"（FR-28 / Q-12 未核实的中性表述）。

### A.9 已知局限（如实说明）

1. **候选覆盖的是"该车经停站"，不是所有车站**。`API-04` 实测返回的是该车次的实际停靠站（K599 为 32 站），因此"多买 1 站"的含义是"多 1 个停靠站"，不是"多 1 个地理车站"。界面必须写"仅覆盖该车经停站"，**不得**说"已穷举所有方案"。
2. **"长区间更容易有票"是经验而非保证**。扩展完全可能全部无票，此时功能产出是"确认没有余地"——界面文案必须把这个否定结果当作有效交付，而不是显示为失败。
3. **Δ 只算票价差，不算其它成本**（如从更远的上车站赶过去的交通费与时间）。本工具不假装能做完整决策，只在票面价格维度上算得准。
4. ~~若拿不到站序则退回 V1.1~~ **v1.3 更新：Q-04 已解决**，`czxx/queryByTrainNo` 游客态可用，该退出条件不再需要触发。但**退出条件本身要保留在文档里**：若该端点日后加登录墙或改参数（RISK-13），FR-26 ~ FR-31 退回 V1.1，**且明确禁止改用码表猜邻近站**——那会产出根本无法上车的候选，比没有功能更坏，也直接违反 NFR-18。
5. **v1.3 新增的残余未知**：`gg_num`/`yb_num`/`srrb_num` 三列的中文席别名尚未确定（官方页面无独立列），当前按"透传不显示"处理；票价席别码全集（实测见 `9 M O D W J I 1 3 4 6`）仍不完整，需实现阶段跨车型补样本。两者都**不影响**主链路，只影响个别席别是否能被正确命名。
