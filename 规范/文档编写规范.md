## 一、每篇文档的固定头部

所有 `规范/`、`需求/`、`设计/`、`计划/` 下的文档，第一屏**必须**是元信息表：

```markdown
# <标题>

| 项 | 值 |
|---|---|
| 文档编号 | <SPEC/PRD/HLD/PLAN-xxx> |
| 版本 | v1.0 |
| 更新日期 | YYYY-MM-DD |
| 关联文档 | [<名称>](./xxx.md) |      ← 可选
| 阻塞项 | <无 / 描述> |              ← 可选
```

开发日志例外，用日期作标题即可。

## 二、编号体系（用于可追溯）

| 前缀 | 含义 | 出处 |
|---|---|---|
| `SPEC-xxx` | 规范条款文件 | 规范/ |
| `PRD-xxx` | 需求文档 | 需求/ |
| `FR-xx` | 功能需求条目 | 需求文档内 |
| `NFR-xx` | 非功能需求条目 | 需求文档内 |
| `BF-xx` | 业务流程（主流程/异常流程） | 需求文档内 |
| `RISK-xx` | 风险条目 | 需求/设计文档内 |
| `HLD-xxx` | 系统设计文档 | 设计/ |
| `TC-xx` | 测试用例 | 测试/用例/ |
| `TASK-xx` | 实施任务 | 计划/ |

**必须**遵守的追溯链：

```
FR-xx  →  设计章节（写明"实现 FR-12"）  →  代码（类/方法注释回指 FR 编号）  →  TC-xx（测试用例覆盖 FR 编号）
```

需求编号一经发布**不复用、不回收**。需求被砍掉时标记 `[已取消 v1.x]` 并保留编号，避免历史文档里的编号指向错内容。

## 三、写作规则

### 语言

1. 正文用中文，技术专有名词保留原文（`telecode`、`train_no`、`async/await`、`SHA-256`）。
2. 一句话只说一件事。避免"考虑到……的情况下，为了……的目的，建议……"这类三层嵌套的长句。
3. 需求描述**主语是人或系统，谓语是动词**：
   - ✅ 系统在用户点击查询后 3 秒内展示结果列表。
   - ❌ 查询结果应该是比较快地被展示出来。

### 可测性

4. 每条 `FR` / `NFR` **必须**带验收标准，且标准可被第三人独立判定真假。
   - ❌ 界面美观、操作流畅、体验良好
   - ✅ 首屏车次列表在 30 条数据下滚动不出现空白帧；从输入到出结果全程不超过 3 次点击
5. 凡是带数字的表述（超时、条数、间隔、体积、日期范围）**必须**写明是"目标值"还是"硬性上限"。

### 明确性

6. 禁用含糊量词：一些、尽量、基本上、比较、可能需要同步调整。改成具体数值或具体条件。
7. 不确定的事实**必须**当场标注，不许伪装成结论：
   ```
   > ⚠️ 待核实：<陈述>。核实方式：<动作>。责任人：<谁>。截止：<日期或阶段>。
   ```
   本项目大量依赖 12306 非公开接口的现状，这类标注是常态，不是缺陷。
8. 每条"不做"都要写清"为什么不做"，防止下一轮讨论又被捞回来。

### 结构

9. 标题层级从 `#` 开始，不超过四级；正文用表格承载对比信息，用列表承载并列信息，别把表格当散文、把散文当表格。
10. 单篇文档超过 400 行时考虑拆分，但**不要**为了拆而拆；一份完整需求文档比五份碎片文档更好读。
11. 图表优先用 Mermaid（GitHub/多数 Markdown 预览可渲染），复杂排版不要依赖 HTML 内联样式。

## 四、版本与修订

1. 文档头版本字段随内容实质变化递增：
   - **主版本**（v1 → v2）：范围增删、结论反转。
   - **次版本**（v1.0 → v1.1）：条目补充、数值调整。
   - 错别字与排版修正不升版本。
2. 每篇 `需求/`、`规范/` 文档末尾**必须**有"变更记录"表：

```markdown
## 变更记录

| 版本 | 日期 | 变更内容 | 原因 |
|---|---|---|---|
| v1.1 | 2026-10-20 | FR-14 优先级 P0 → P1 | 亲友反馈收藏用得少 |
```

3. 需求侧的所有变更，同时汇总一行到 [`需求/变更记录.md`](../需求/变更记录.md)，便于回看范围蔓延轨迹。

---

## 五、禁止事项

- ❌ 同一份文档里出现两个互相矛盾的数值，靠"以最新为准"兜底。
- ❌ 用"（此处省略）"、"……"、"待补充"充当内容交付。留白要用第七节的待核实格式，写明谁来补。
- ❌ 把与特定一次任务相关的过程描述写进长期文档（"本次改动增加了……"），这类内容属于开发日志。
- ❌ 新建与既有文档主题重叠的"XX 补充说明.md"、"XX v2.md"。改原文档，升版本号。
