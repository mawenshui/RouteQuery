## 一、合规边界

### 允许

- 以用户显式动作触发的余票、时刻表、经停站、接续换乘**查询**。
- **区间扩展查询（"多买几站"）**：对某趟已购车次不可网上购票的区间，用户显式点选后，查询同一车次若干**更长区间**的余票与票价，算出多花金额供用户自行决策。**只读、只展示、只跳转**；不存在自动下单、锁票、占位。
- 结果本地展示、本地筛选排序、本地收藏与历史。
- **WebView2 内嵌 12306 官方登录页**，由用户本人输入凭据；应用仅复用登录后留在 WebView 容器内的会话，用于换取中转与经停数据。
- 生成跳转到 12306 官方页面的链接，把选座、下单、支付全部留给官方。

### 禁止（无条件）

| 禁止事项 | 为什么 |
|---|---|
| 应用采集/接收/存储/转发密码与验证码答案；自行构造登录请求 | 凭据一旦经过程序代码，风险就从"IP 被查多了"变成"亲友账号被风控 + 密码交给非官方程序"，且这是抢票工具的通用起点 |
| 识别、绕过、自动填写验证码 | 直接对抗技术保护措施 |
| 下单、占座、候补、支付、自动提交任何交易表单 | 属交易行为，超出查询定位 |
| 高频轮询、批量并发、多 IP/代理池、指纹伪装 | 对官方系统构成压力，是"抢票工具"的技术特征 |
| 把接口能力包装成对外 API 或收费服务 | 从个人工具变成商业爬虫 |
| 转发/公开 **Cookie、会话凭据、抓取凭证**，或把接口能力共享给代管账号的第三方 | 凭据一旦扩散就无法收回，且被冒用的是亲友的账号 |

### 关于"接口技术细节可否公开"（v1.4 明确）

本项目的**接口实测记录**（列布局、路径后缀行为、编码规则）允许随本公开仓库发布，理由与边界如下：

- **允许**：以个人学习、同类工具互鉴为目的，在公开仓库中记录观测到的响应结构与解析方法。这类信息在多个开源项目中已长期公开存在，本文档的记录方式也是"观测结果 + 语义未确认项如实标注"，不含任何可用凭据。
- **禁止**：提交任何 **Cookie 值、会话密文、账号标识、代理端点、抓取凭证池**；`测试/接口样本/` 只允许存放已确认无凭据的公开时刻表响应片段。
- **禁止**：把文档写成"操作手册"式的内容——即教人如何绕过验证码、如何维持批量抓取、如何组织多账号。本项目的文档定位始终是"为什么这样做是必要的、以及边界在哪里"。
- **责任边界**：本仓库不构成对第三方使用方式的授权或指导。任何人据此构建自动购票、批量抓取工具，属 AGENTS.md 第五节明确禁止的形态。

### 判定原则

新需求到来时先问一句：**这个功能是"帮人看懂官方数据"，还是"替人操作官方系统 / 挤占官方资源"？** 后者一律拒绝并说明理由。

- 涉及登录的需求额外问第二句：**密码有没有可能经过我的代码？** 只要答案是"有可能"，方案就是错的。
- 会产生批量请求的需求额外问第三句：**这一个用户动作最多会产生多少次官方请求？它是否在官方最紧张、风控最敏感的时刻被用得最多？** "多买几站"在这句话上是本项目的风险顶点：它天然只在春运这类时刻被使用，也就是官方最脆弱的时刻——**功能价值与资源压力恰好同向**，所以必须靠预算硬上限、串行、间隔和"让用户自己决定要不要开始"来对冲，而不是靠"用户应该有分寸"。

> 官方**仍返回 302 → passport**。采到的 Cookie 名单为

> （已改为并集读取两个官方主机，见 v1.8）；② 用户当时并未真正完成登录。
> **结论未定**，必须再实测一次才能写解析——把"猜出来的换乘结构"当成官方数据交付是本规范禁止的第一号错误。

> **2026-10-10 登录态实测（第二次，采集已改为并集）——仍然否定**：
> ① 并集读取 `kyfw.12306.cn` + `www.12306.cn` 后采到的还是同样 7 条：
> `SF_cookie_2`、`cursorStatus`、`guidesStatus`、`highContrastMode`、`BIGipServerpassport`、`BIGipServerotn`、`uKey`；
> ② 带这套 Cookie 请求 `API-03` → **302 → `/otn/passport?redirect=/otn/lcQuery/query`**；
> 换成中转页 `Referer` + `API-Referer` 再试，**结果一样**——所以不是请求头形态的问题；
> ③ 用户确认内嵌页面右上角已显示其用户名，即**浏览器里确实是登录状态**；
> ④ 查 WebView2 私有目录里持久化的 Cookie 只有 5 条（3 条界面偏好 + 2 条 `_uab_collina`），
> 说明上面那几条是**会话级**（不落盘，只在浏览器进程内）。
>
> **由此得出的判断**：缺的不是"采集漏了哪一条"，而是**业务会话的建立过程**——浏览器是通过跟随
> `passport` 的那条 302 链才拿到可用会话的，而本应用的客户端按设计**不跟随重定向**
> （只跟随"接口改名"那一类，见本节规则 4）。
>
> **两条候选路，第二条需要用户决策**：
> **A**（不碰红线）：让用户在内嵌页里自己点进"中转换乘"页，再由用户点"我登录好了"采集——
> 这是把 WebView 当浏览器用，握手由官方页面自己完成。
> **B**（踩线，需明确授权）：让程序跟随 `passport` 的 302 链把会话跑出来——这与
> AGENTS 第五节第 2 条"禁止自行构造登录 HTTP 请求"相邻，不能由实现者自己决定。
> **在拿到一次真实成功的样本之前，`API-03` 的响应结构仍是未知的，中转解析不得开工。**
| **`API-04`** | 车次经停站时刻 | **`GET /otn/czxx/queryByTrainNo?train_no=&from_station_telecode=&to_station_telecode=&depart_date=yyyy-MM-dd`** → **200，`data.data` 为 32 个对象的数组**，字段为**具名字段**（`station_no`/`station_name`/`arrive_time`/`start_time`/`stopover_time`/`train_class_name`/`start_station_name`/`end_station_name`/`isChina`/`isEnabled`/`service_type`/`country_code`/`country_name`/`station_train_code`） | ✅ **游客态可用**（实测） | 空数组或失败判错误并提示；**禁止**用码表推断经停站替代 |

> ✅ **Q-04 已解决（2026-10-09 第二次核实）**。此前实测失败的真正原因是**端点错了**：正确端点是 `czxx/queryByTrainNo`（车次信息，`stopStation` 插件调用它），而不是 `queryTrainInfo/query`。参数名与历史版本一致，日期必须是 `yyyy-MM-dd` 带连字符格式。样本已归档 [`测试/接口样本/czxx-经停站样本.json`](../测试/接口样本/czxx-经停站样本.json)。**关键结论：游客态可用，且响应是具名字段数组，不需要列布局表**。

### 票价来源结论（本项目的取舍）

`列 39（yp_info_new）` 解码值与官方 `API-06 queryTicketPrice` 返回**逐项一致**（G6701：174.00/79.00/49.00；K599：21.50/102.50/67.50），实测见 [`queryTicketPrice-票价样本.json`](../测试/接口样本/queryTicketPrice-票价样本.json)。

**因此本应用只从 `API-02` 的列 39 取票价，不额外调用 `API-06`**。理由不只是省一次请求：`API-06` 在 curl 直连下被 302 到错误页，只在真实页面上下文里可用——依赖它等于依赖"我们模拟了浏览器流程"，脆弱且与 SPEC-007 第三节的"请求头最小必要"取向相冲突。对"多买几站"而言，这个结论**决定了请求预算是否成立**：每个候选 1 次请求即可同时拿到余票与票价，若还要单独取价则预算会翻倍。

- 价格串切分：**每 10 字符一条记录** = `席别码(1) + 以分为单位的价格(6) + 附加标记(3)`。
- **同一席别出现多条时取第一条**——已由官方接口反向验证：首条与页面显示一致，次条（如 `O=49.03`、`1=21.53`）**官方并不展示**。
- 无座票价在官方返回里等于同席别座席价（`WZ` 与 `O`/`1` 同值），界面对"无座"应显示与对应座席相同的价，不要显示成 0 或缺失。
- 附加标记（`000`/`003`/`021`/`330`）业务含义未知，**忽略但不参与计算**，不参与筛选与排序。

### 跨车型布局验证（2026-10-09 第二次核实）

北京 BJP → 保定 BDP，2026-10-12，**124 条记录，覆盖 C/D/G/K/T/Z 六种车型，列数恒为 58**。

结论：**列数与位置不随车型变化**，`LeftTicketColumnLayout` 用单一固定列数是成立的；`StructureValidator` 的"列数 == 58"自检有实测依据。列语义随后由**官方渲染脚本的具名字段赋值代码**确定（见上表），并与页面 DOM 同瞬间逐格验证通过。

> ✅ **Q-10 已解决**（见上方"列 20–33"与逐格验证结果）：余票权威列为 **列 20–33**；列 34 是 `yp_ex`，与余票无关。
> ✅ **Q-05 已解决**：同席别多条价格取第一条——官方 `queryTicketPrice` 只返回首条对应的值，次条不展示，故"取首条"不是保守假设而是**被官方接口反向验证过的正确策略**。
>
> 保留的纪律：本次能定论是因为找到了**官方代码本身**这一权威来源，而不是因为取值看起来合理。文档里凡是"看起来合理所以这样定"的结论，都属于未完成项；今后遇到列漂移，先找官方脚本再改表。

### 硬性解析规则

1. 列布局**必须**收敛到单一版本化描述表（`LeftTicketColumnLayout`），全库唯一允许出现裸下标的位置；每个列位**必须**记录来源标记（`Confirmed-ByOfficialScript` / `Confirmed-ByObservation` / `Unverified`）与核实日期。
2. 解析前**必须**做结构自检三项：列数 == 58、车次号列匹配 `^[GDCZTKLY]\d{1,4}$`、时刻列匹配 `^\d{2}:\d{2}$`。任一项不过 → `ParseFailure`，**停止出数并明确提示"数据格式变更，需升级"**，禁止部分解析成功就当作正常结果渲染。列数 58 已跨 C/D/G/K/T/Z 六车型 124 条样本验证。
3. 未知席别码**不得**导致异常，降级为原样透传并写日志。
4. 加密列（0 `secretStr`、12 `yp_info`）**不得**尝试解密或推测内容，只作为透传标识使用。页面脚本含 `SM4`/`base64js`，说明官方自有解密逻辑——**本项目不得跟进**，那是越界的开始。
5. **余票三态必须显式区分，且判定式取自官方代码原文（v1.7 更正）**：
   - `有票` = 原始值为 `有` 或数字；`无票` = `无` 或空。
   - `可候补` = **原始值恰为 `"无"`** 且 **该席别不是无座/其他**（官方键 `WZ_` / `QT_`）且 **`houbu_train_flag`（列 37）== "1"`**。
   - **列 37 是车次级标记，不能单独用来判定某席别可候补**（实测 122 条中 97 条为 `1`，其中 48 条仍有票）。列 38 `houbu_seat_limit` **只影响颜色样式，不参与标签判定**——v1.5 曾写成"由列 37/38 判定"，那是错的。
   - **"只看有票"筛选中，候补不算有票。**
6. **`canWebBuy` 不得施加 `^[YN]$` 校验**（v1.7 新增）。实测取值域含 `IS_TIME_NOT_BUY`；若把它当结构异常，会让所有尚未开售的车次触发 `ParseFailure` 并**整批不出数**——那正是自检规则本要避免的错误。
7. **星号 `*` 不是余票值**（v1.7 新增）。实测 47 条含 `*` 的车次，其 `canWebBuy` 全部为 `IS_TIME_NOT_BUY`；Y/N 车次中 0 条含 `*`。即 `*` 表示"尚未开售、官方未给该项数据"。未开售另有第二种表现：**整行席别列全空**（如 G1025）。因此**"是否开售"只能以列 11 为判据，不得由席别列反推**；席别列里的未知符号一律原样透传，禁止映射成"有票/无票/0"。
8. **日期越界与被拒绝同形**（v1.7 新增）。实测预售期为**含当天共 15 天**（2026-10-10 时可查到 10-24，10-25 起返回 HTML 错误页）。越界响应与风控拒绝的形态**完全相同、无法区分**，因此日期范围校验**必须**在本地、发请求之前完成（FR-04），绝不依赖服务端反馈来发现非法日期。
9. **数据来源单一性（硬约束，最高优先级）**：所有列车、余票、票价、经停站、换乘数据**只能**来自 12306 官方接口。任一项取不到时，**唯一正确行为是报错并说明原因**；**禁止**以任何方式替代，包括：用站点码表推断经停站、用历史缓存冒充当前余票、用里程或席别常识推算票价、用第三方数据源补齐、把"取不到"显示成"无票"或"0 元"。
   理由：这个应用的输出是**亲友的出行与购票决策依据**。替代来源产生的数字看起来和真数据一模一样，但没有任何机制能保证它正确——它比空白危险得多，而且一旦开了口子，"降级"会在代码里被到处复用，最后没人分得清屏幕上哪个数是官方的。

## 三、会话与登录态

1. 查询前需向官方站点建立基础会话（`GET /otn/leftTicket/init` 获得 `BIGipServerotn`、`SF_cookie_2` 等）。会话**只**保存在内存或本机用户目录。
2. **登录态的唯一来源是 WebView2 内的官方页面**。应用侧只允许：读取 WebView 容器的 Cookie 集合 → 存入受保护存储 → 在后续官方请求中附带。禁止在应用内出现任何接收密码的接口。
3. 登录态存储**必须**用 DPAPI（当前用户范围）加密后落 `%LOCALAPPDATA%`；**禁止**明文；**禁止**写日志；**禁止**出现在崩溃转储与错误提示文本中。
4. **必须**提供"退出并清除登录状态"，同时清除 WebView 容器 Cookie 与应用侧加密副本。
5. 登录态过期时**不得**静默重登或猜测，行为是：清掉本地会话 → 提示"需要重新登录官方账号" → 打开官方登录页。
6. 请求头最小必要原则：只设 `User-Agent`、`Referer`、`Accept` 等使请求形似正常浏览器访问的字段。**不得**构造指纹池。
7. 若官方返回非 JSON（HTML 提示页、登录页、验证码页、意外 302），一律判为 `UpstreamRejected`：**立即停止后续请求**。注意"302 到 `passport`"是**预期的登录要求**，与风控的"302 到异常页"必须区分处理，前者引导登录、后者停止。

## 四、频率与节流（硬性数值）

| 项 | 目标值 | 硬性上限 |
|---|---|---|
| 单次用户动作触发的官方请求数 — **基础查询** | 1 次 | **≤ 3 次**（直达 1 + 中转两段 2；或直达 + 会话初始化） |
| **区间扩展（v1.3 新增）** — 单次"多买几站"动作 | ≤ 6 次 | **默认预算 ≤ 10 次，硬上限 ≤ 12 次**；候选超出预算时只做优先级最高的前 N 个，并明示"还有 M 个候选未查询" |
| 区间扩展 — 站数上限 K | 默认 3 | **1–10，应用层强制裁剪**。K 与上面的次数预算是**两个独立刹车**：K 决定候选规模，预算决定实际打出去多少次，两者都不许省略 |
| 区间扩展 — 中断与失败 | 可随时中断 | 遇 `UpstreamRejected` 或 `ParseFailure` **整批立即中止**，禁止"跳过这个候选继续下一个" |
| 两次查询最小间隔 | 无强制 | **≥ 3 秒**，间隔内点击给出提示，不排队发请求。**扩展批次内部同样适用，不得为压缩耗时缩短**——按 10 候选算，这自然把一次扩展拉到 ≥30 秒，那是**有意的结果**而不是缺陷 |
| 自动/后台发起的请求 | 0 | **0**（V1 无任何定时器发起官方请求，登录态存在也不放开） |
| 并发请求 | 1 | **1**（同一时刻仅一个在途官方请求，含 WebView 之外的直连请求；扩展严格串行） |
| 重试次数 | 0 | 最多 1 次，且仅限 `NetworkUnavailable`；`UpstreamRejected`/`ParseFailure` 不重试 |
| 单日请求计数 | 提示 | ≥ 200 次时界面提示"今日查询较多，请降低频率"；登录态下阈值收紧到 **100 次**（账号风险高于 IP 风险）；**扩展请求全额计入**，且界面必须显示剩余额度 |
| 经停站/中转等钻取请求 | 每次展开 1 次 | 展开同一车次**不重复请求**（会话内缓存）；区间扩展所依赖的经停站序同样会话内缓存 |

V2 的"余票提醒"若要引入轮询，**必须**先修订本表：轮询间隔下限、随机抖动、单条监控的每日请求预算、且登录态下的账号风险要单独评估。不得在 V1 预埋轮询代码。

**"最小间隔 3 秒"的适用边界（实现阶段澄清，不是放宽）**：该间隔适用于**两次用户动作之间**，以及**扩展批次内每一次候选调用之前**；**不适用**于同一个动作内部的连续步骤。理由：一次直达查询天然包含"会话初始化 + 取数"（官方页面自身也是连着发这两次），若在它们之间也卡 3 秒，应用将无法工作。约束的强度由**单动作预算**保证（基础 ≤3、扩展 ≤12），而不是由动作内部的人为停顿保证。

**区间扩展为什么单独成表，而不是并进"基础查询 ≤3 次"**：一个统一的低上限会让扩展功能在设计上不可实现，实现者于是面对两个坏选项——默默绕开约束，或者砍掉功能。把约束按动作类型拆开并各自给出硬上限，规范才是可执行的。

**代价也必须说清**：本项目由此第一次出现"一个用户动作可产生十次以上官方请求"的形态，而它恰好在官方压力最大的时刻被使用。因此审计口径必须存在：`RequestGate` 按动作类型分别计数并写日志，发布前核对扩展批次的实际请求数；对应需求侧条目见 PRD-001 的 NFR-17 与 RISK-21。

## 五、缓存优先策略（同时也是降频手段）

| 数据 | 位置 | 有效期 |
|---|---|---|
| 站点码表 | 本地文件（内置一份带日期） | 长期；超 90 天**提示**可手动更新（阈值以 PRD FR-18 为准，v1.6 前此处写 30 天与需求不一致），不自动请求 |
| 站点模糊匹配索引（含同城聚合） | 内存 | 进程生命周期 |

余票是强时效数据：**禁止**跨会话缓存并当作当前余票展示。缓存条目**必须**在界面显式标注时效。

## 六、数据使用与隐私

1. **除官方接口外不得有任何第三方出站**（无遥测、无统计、无广告、无崩溃上报）。v1.6 起允许**唯一一项例外**，且边界必须逐条守住：

   | 例外 | GitHub Releases 版本检查（FR-36） |
   |---|---|
   | 允许的目标 | 仅 GitHub 的版本发布接口，用于取最新版本号 |
   | 允许的频率 | **仅应用启动时一次**。不定时、不轮询、不因用户操作重复发起 |
   | 允许携带 | 无。请求中**不得**含查询记录、收藏、站点、日期、机器名、用户名或任何标识符 |
   | 必须可关闭 | 设置页提供开关；关闭后非官方出站为 **0**（抓包可验证） |
   | 失败行为 | **静默忽略**。不得弹错误框、不得影响任何其他功能 |
   | 禁止扩张 | 不得借"更新检查"之名加入配置下发、功能开关、灰度、日志上传或远程Kill Switch——那会把个人工具变成有控制端的服务，是第五节"禁止包装成商业服务"的同一条线 |

   任何新增的非官方出站都必须先修订本节并说明为什么不能由用户手动完成。
2. 查询条件、收藏、历史、日志只存本机；`README` 与发布包 `使用说明.txt` **必须**用一句话讲清。
3. **引入登录态后新增的隐私义务**：本机会话等同"亲友的 12306 账号在本机处于登录状态"。因此：
   - 应用**必须**在界面常驻显示当前登录状态（含"已登录 / 未登录"），禁止静默持有他人账号会话。
   - 共享电脑上，退出登录必须是显眼且一键可达的默认动作；`使用说明.txt` **必须**写明"在他人电脑上使用后请清除登录状态"。
   - **禁止**读取、展示、缓存任何登录后才可见的个人数据（订单、常旅客、12306 账号资料）。只允许用于换取中转/经停查询结果。
4. 本地日志**必须**包含：时间、接口编号、错误分类、脱敏响应片段（截断）。**禁止**记录 Cookie 值、`train_no` 之外的用户标识。

| 编号 | 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|---|

| RISK-12 | 列语义在官方脚本变更后再次漂移，而本项目仍按旧表解析 | 中 | 数据静默失真 | 布局表带来源标记与核实日期；自检不过即停；每季度按第八节复查官方脚本中的赋值代码 |
| RISK-13 | `czxx/queryByTrainNo` 未来加登录墙或改参数（历史上 `queryTrainInfo` 就已换过） | 中 | 经停钻取与"多买几站"同时不可用 | 该端点失败时**报错并说明**；"多买几站"入口整体置灰。**禁止**改用码表推断经停站来"保功能"——宁可功能不可用，也不输出猜测值 |

| RISK-07 | 站点码表过期（新车站查不到） | 中 | 部分 OD 失败 | 内置码表标注日期；手动更新；未命中时引导改用站名片段或上级市名 |
| RISK-08 | 触发 IP 风控 | 中 | 一段时间无法查询 | 节流表严格执行；识别为 `UpstreamRejected` 后停止请求；提示"稍后再试"而非刷屏重试 |
| RISK-09 | 亲友误认为这是官方 / 可购票工具 | 中 | 信任与责任边界模糊 | 常驻非官方声明；无任何交易入口；登录页保持官方原样可见地址信息 |
| RISK-10 | 需求向"自动刷票/代下单"漂移 | 中 | 合规性质变 | 第一节作为拒绝依据；发布前固定合规自查 |

## 八、维护预案

1. 列布局、席别码表、接口路径前缀、结构自检规则**必须**可外置为本地配置，使"官方改字段"这类修复可以只更新配置而不重发整个应用；至少在重发新版时不需要改动 UI 层。
2. 每次接口变更后**必须**：补 `测试/接口样本/` 样本 + 契约测试 → 更新本文档第二节 → 填实测日期 → 升修订版。
3. 每季度检查：接口可达性、列数与自检规则是否仍通过、码表是否需更新、依赖包安全更新。结论写入 `开发日志/`。
4. 本文档第二节是**唯一**允许记录具体列下标的地方；代码里的下标只允许出现在布局描述表中。
