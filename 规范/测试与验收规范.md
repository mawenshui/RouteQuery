## 一、测试分层

| 层次 | 覆盖对象 | 是否联网 | 工具 | 优先级 |
|---|---|---|---|---|
| **契约测试** | 12306 响应解析器 | ❌ 用录制的样本 | xUnit + `测试/接口样本/` | **P0，本项目最高价值** |
| 单元测试 | 筛选、排序、比价、历时计算、跨零点、日期范围校验、三字码匹配 | ❌ | xUnit | P0 |
| 集成测试 | 缓存读写、码表加载与版本迁移、配置持久化 | ❌（本地临时目录） | xUnit | P1 |
| 界面手工验收 | 真实查询链路、视觉、交互反馈 | ✅ 真实请求 | 人工 + 截图 | P0 |
| 冒烟测试 | 发布包能否在别人机器上双击跑通 | ✅ | 干净 Windows 账户实测 | P0 |

**为什么契约测试是 P0**：本应用唯一真正的不可控因素是外部接口。解析逻辑一旦回归，整个应用变成摆设；而这类 bug 在 UI 测试里表现为"网络错误"，容易被误判成偶发。所以解析器必须有样本驱动测试兜底。

---

## 二、契约测试细则

1. 每个外部接口至少 3 类样本：正常有结果、正常无结果、结构异常/被风控。
2. 样本文件命名：`<接口简称>-<场景>.json`，如 `leftTicket-正常.json`、`leftTicket-无结果.json`、`leftTicket-风控页.html`。
3. 样本**必须脱敏**：移除 Cookie、真实 IP、账号相关标识。
4. 解析测试**必须**断言字段映射的正确性而不是仅断言"不抛异常"：
   - 车次号、发到时刻、历时、出发/到达站名、各席别余票与票价至少各断言一条具体值。
5. **必须**有"列布局漂移"的守卫测试（取代早期"mapper 乱序"设想，因实测响应**已无 `mapper`**）：
   - 样本中删除或改错一列（如把时刻列换成非 `HH:mm` 的值）→ 解析器**必须**抛 `ParseFailure`，而**不是**返回一个字段错位的正常对象。
   - 样本列数由 58 变为 57 → 同样判为 `ParseFailure`。
   - 出现未登记的席别码 → 不抛异常，原样透传并写日志。
   这三条是 RISK-01（静默给出错误数据）唯一的自动化防线，比任何 UI 测试都重要。
6. **必须**断言字段位置取自版本化布局描述表，而不是散落在解析代码里：测试可直接读取该表与样本比对列数。
7. 断言日期/时刻/票价使用强类型比较（`DateOnly`、`TimeSpan`、`decimal`），不做字符串模糊比较。票价断言**必须**含解码用例：`9174400000M083600000O049800000` → `1744.00 / 836.00 / 498.00` 元。

## 三、单元测试重点场景（本项目易错点清单）

```
□ 站点模糊匹配：输入"北京"命中 北京/北京南/北京西/北京朝阳…；输入"bj"命中规则明确
□ 同城市多站：OD 为同城两站（北京南→北京西）时的输入校验
□ 日期边界：预售期首末日；昨天/超期日期必须被本地拦截
□ 历时计算：跨零点夜车；到达时间 == 发车时间（异常数据）
□ 席别缺失：字段为空/为"--"/为"无"三种表示，均归一化为"无票"
□ 票价缺失：显示为"—"，且参与"最便宜"排序时不被当成 0
□ 排序稳定性：同一耗时下按发车时间次级排序
□ 筛选组合：只看有票 + 车型 + 时段 三者叠加
□ 中转方案：两段车次时间重叠（换乘不足）时不得生成方案；跨夜、隔天方案
□ 取消语义：新查询开始后，旧请求的返回结果必须被丢弃
—— 以下为"多买几站"（v1.2 新增）——
□ 候选区间必须**真包含**目标区间；不满足的候选不得出现
□ 目标站为始发站 / 终到站 / 全程票三种边界下的候选集与"零请求"要求
□ p+q ≤ K 约束；K=10 时候选数远大于预算，截断与"未查询数"必须正确
□ Δ 必须同席别对齐；一侧价格缺失 → "无法计算"，禁止落成 0
□ **Δ 为负值必须判为异常**（说明列位或席别对齐错了），不得当正常数据渲染
□ 扩展批次内间隔仍 ≥3 秒、并发仍为 1 —— 这条测试存在的意义是防止有人为了"快一点"把它改掉
□ 硬上限 12 不受配置影响：把 K 配成 10、把预算配成 99，实际请求数仍 ≤ 12
```

## 四、界面手工验收清单（每轮发布前必做）

| 编号 | 步骤 | 通过判据 |
|---|---|---|
| TC-U1 | 冷启动到可输入 | 主窗口出现 ≤ 2 秒，无白屏闪烁 |
| TC-U2 | 输入两个站名+默认日期，点查询 | 10 秒内出结果；等待期间有明确加载态；按钮不可重复触发 |
| TC-U3 | 查询一个明显无车的冷门 OD | 展示"无直达车次"空状态，而不是报错弹窗 |
| TC-U4 | 断网后查询 | 人话提示 + 重试按钮；恢复网络后重试成功 |
| TC-U5 | 结果按最慢/最早/最便宜切换排序 | 首条即时变化，滚动位置重置到顶部 |
| TC-U6 | 点开任一车次经停站 | 站点顺序正确，当前 OD 两站在列表中高亮 |
| TC-U7 | 查询一个中转 OD | 直达与中转分区展示，换乘候车时长可见 |
| TC-U8 | 保存常用线路 → 关闭 → 重启 | 重启后收藏仍在，一键重查可用 |
| TC-U9 | 点"到 12306 官方查看" | 用默认浏览器打开官方页面，带正确参数 |
| TC-U10 | 连续快速切换查询条件 5 次 | 界面不卡死，最终展示的是最后一次请求的结果 |
| TC-U11 | 100% / 125% / 150% 缩放 | 文字不截断、按钮不重叠 |
| TC-U12 | 干净账户安装发布包 | 双击可用，无需另装运行库 |
| TC-U13 | 打开内嵌登录页 | 页面为官方原样，地址栏/域名对用户可见可核对；应用中无任何"输入密码"的界面 |
| TC-U14 | 登录成功后回到应用 | 登录状态常驻可见；中转查询可用；未登录时中转区给出"需登录"引导而非报错 |
| TC-U15 | 点"清除登录状态" | 立即失效：再次查中转回到未登录态；检查加密会话文件已删除或被置空 |
| TC-U16 | 全盘搜索本机存储与会话 | 任意位置检索不到明文密码与 Cookie 值；日志文件中无 Cookie 字符串 |
| TC-U17 | 触发一次列自检测试（人为喂异常样本） | 界面显示"数据格式变更，需升级"，且不渲染任何错位车次 |
| TC-U18 | 对一趟不可网上购票的车次点"多买几站"，K=3 | 显示预估耗时与进度；结果逐条即时插入；每条同时可见"多买 X 站"与"多花 ¥Y"；日志计数 ≤ 预算 |
| TC-U19 | 扩展执行到一半点"停止" | 已获得的候选结果**保留可见**，不再发新请求 |
| TC-U20 | 扩展批次中人为制造一次风控响应（或喂样本） | **整批立即中止**，不跳过继续；直达区不受影响；文案为"稍后再试"而非"重试"刷屏 |
| TC-U21 | 把上限设为 1 / 10 / 0 / 11 / 空 | 0、11、空、非数字被拒绝或钳到边界；候选数与预估耗时随 K 变化；实际请求数永远 ≤ 硬上限 |
| TC-U22 | 目标站即该车次始发站且终到站（全程票）时点扩展 | 候选为 0，界面说明"已是全程票，无法再扩展"，**且不发起任何官方请求** |
| TC-U23 | 逐条比对扩展金额 | 用官方页面分别查目标区间与候选区间票价，Δ 与界面显示一致；缺失价格处显示"无法计算"而不是 0 |

任何一条不通过，**不得**进入发布阶段；若因客观条件无法验证，必须在测试报告写明"未验证 + 原因"，不许默认通过。

## 五、完成定义（DoD）

一个 `TASK` 视为完成，当且仅当：

1. 代码编译通过且 0 新增警告。
2. 对应的单元/契约测试已存在并通过。
3. 涉及的 `FR-xx` 验收标准逐条对照，人工可判定达成。
4. 界面类任务附截图到 `设计/界面/` 或测试报告。
5. 规范自查清单（SPEC-004 第八节）打完勾。
6. `计划/` 中该任务状态更新。

## 六、红线

- ❌ 为了让测试通过而修改断言去迁就实现（除非确认断言本身错了，并在开发日志写明）。
- ❌ 跳过契约测试直接依赖真实网络"看着对"。
- ❌ 声称"UI 已验证"但未实际运行应用。无法验证时必须明说无法验证。
- ❌ 用 `Assert.NotNull(x)` 冒充完整断言。
