## 二、约束等级用词

全套规范只用三个词，含义固定，不得混用：

- **必须**：违反即为缺陷，评审时应当场打回。
- **应当**：默认遵守；违反时在开发日志写明理由。
- **可以**：可选做法。

---

## 三、"全流程可控"如何实现

可控不等于流程繁重，而是让每一步都能回答三个问题：**现在在哪个阶段 / 这个阶段的产物是否齐全 / 下一步的准入条件是什么。**

| 控制点 | 载体 | 谁来验证 |
|---|---|---|
| 需求可追溯 | 需求文档的 `FR-xx` / `NFR-xx` 编号 | 设计与代码注释回指编号 |
| 阶段不越界 | SPEC-003 的五道门禁 | 动手前先检查上游文档是否存在 |
| 决策不丢失 | `开发日志/` 决策记录 | 会话结束时补写 |
| 变更不失控 | `需求/变更记录.md` + 版本号 | 每次需求变化追加一行 |
| 接口变更不扩散 | SPEC-007 的数据层隔离 | 代码评审检查 URL 是否泄漏出 `RouteQuery.Data` |
| 发布可回退 | SPEC-006 的版本号与发布物清单 | 发布前核对清单 |

## 四、规范的修改规则

1. 修改任何规范**必须**同步升级该文件的"版本"字段，并在本文档第五节留痕。
2. 降低约束（"必须"改"可以"）需在开发日志说明原因，防止规范被逐步放空。
3. 新出现的、反复踩到的问题，优先沉淀为规范条款，而不是留在口头约定。
