## 一、五个阶段与门禁

```
① 需求 ──▶ ② 设计 ──▶ ③ 计划 ──▶ ④ 实现 ──▶ ⑤ 验收与发布
   门禁1      门禁2      门禁3      门禁4         门禁5
```

"门禁"意思是：**上游产物不齐全时，下游不许开工**。这不是官僚流程，而是防止凭印象写代码导致返工——尤其是本项目的外部接口随时可能变，没有记录就无法判断"当初为什么这么写"。

---

### ① 需求阶段

| 项 | 内容 |
|---|---|
| 产出 | `需求/YYYY-MM-DD-<主题>-需求文档.md`（含 `FR`/`NFR`/`BF`/`RISK` 编号、验收标准、不做什么） |
| 准入 | 用户提出想法 |
| 准出 | 用户确认三件事：**范围边界**、**优先级排序**、**不做什么清单** |
| 禁止 | 在本阶段写代码、建工程文件、拉依赖 |

需求阶段必须完成的确认动作：把影响技术选型的开放问题一次性问清（用户是谁、核心场景、分发方式、外部依赖边界、实现栈），而不是边写边猜。

### ② 设计阶段

| 项 | 内容 |
|---|---|
| 产出 | `设计/YYYY-MM-DD-<主题>-系统设计.md`：分层与模块划分、数据模型、接口依赖清单与降级策略、界面信息架构、错误处理策略、测试策略 |
| 准入 | 需求文档已确认 |
| 准出 | 每个 P0 功能都能在设计里找到对应模块；每条外部依赖都有失败处理方式 |
| 禁止 | 在本阶段实现业务逻辑；允许建 `src/` 目录骨架和 `.sln`，但不写功能代码 |

设计阶段必须回答的**本项目特有**问题（2026-10-09 已有实测结论，见 SPEC-007 第二节）：列布局漂移时如何保证不静默出错误数据（而非"如何避免用下标"——实测已无映射表可用，下标不可避免，要设计的是把下标单点化并在失效时立刻停手）；站点码表从哪来、多久更新、更新失败怎么办；被风控时应用的表现；需要登录态的功能如何在应用不接触凭据的前提下拿到会话。

### ③ 计划阶段

| 项 | 内容 |
|---|---|
| 产出 | `计划/YYYY-MM-DD-<主题>-实施计划.md`：`TASK-xx` 列表，每项含涉及文件、完成判据、依赖关系、规模（小/中/大） |
| 准入 | 设计文档已确认 |
| 准出 | 任务粒度小于"一次会话可完成"；任务顺序体现依赖（如码表先于查询） |

### ④ 实现阶段

| 项 | 内容 |
|---|---|
| 产出 | `src/` 代码 + 对应测试 + `开发日志/` 记录 |
| 准入 | 有计划任务编号 |
| 准出 | 编译通过、相关测试通过、代码评审自查清单打完勾 |

**每次改动的最小动作序列（必须按序执行）**：

1. 读 `AGENTS.md` 与本任务相关的规范。
2. 定位受影响的模块，读现有代码，不凭记忆改。
3. 说明本次改动范围，得到用户认可后再动手（涉及删除文件、改接口契约、加依赖时必须先问）。
4. 编辑，保持改动最小，不顺手重构无关代码。
5. 编译 / 跑测试。
6. 失败先查根因，禁止用 `try-catch` 吞异常、禁止删测试来"通过"。
7. 有实质决策时补写开发日志。

### ⑤ 验收与发布阶段

| 项 | 内容 |
|---|---|
| 产出 | `测试/报告/` 验收结论 + `发布/变更日志.md` + `发布/<版本号>/说明` |
| 准入 | 全部 P0 任务的代码合入且构建通过 |
| 准出 | 见 SPEC-005 的"完成定义（DoD）"，以及 SPEC-006 的发布前清单 |

## 二、返工规则

| 发现问题的时机 | 处理方式 |
|---|---|
| 实现时发现需求有歧义 | **停下**，回需求文档补明确条款，再继续 |
| 实现时发现设计不可行 | **停下**，更新设计文档并说明推翻原因，不默默改成另一套 |
| 验收时发现漏了某条 FR | 先判断是"没实现"还是"没写进需求"，再决定补代码还是补需求；禁止静默扩大范围 |
| 上线后发现接口变了 | 记 `RISK` 触发事件 → 更新数据层与 `测试/接口样本/` → 升版本发布 |

**禁止**：口头改需求。需求变化必须落到文档，否则"可控"就无从谈起。

---

## 三、并行与依赖

1. 只有互不依赖的任务才并行（例如"界面主题"与"解析器单测"）。
2. 涉及同文件的改动**必须**串行。
3. 对 12306 接口的探查性任务不得与功能开发并行推进结论——探查结果先进设计文档，再驱动代码。

---

## 四、会话协作约定

- 用户说"先只出文档"时，绝不动代码。
- 用户说"继续"时，按 `计划/` 里的下一个 `TASK` 推进，不跳跃、不提前实现未来功能。
- 上下文被压缩或换会话时，靠 `README.md` 状态表 + `开发日志/` + `计划/` 恢复，不靠对话记忆。
